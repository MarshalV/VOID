# Отчёт о безопасности VOID P2P Messenger

> Дата анализа: 27 апреля 2026  
> Проанализированные файлы: `src/crypto.rs`, `src/main.rs`, `src/file_transfer.rs`

---

## 1. Что защищено хорошо

### Транспортный уровень (Noise Protocol)
Весь P2P трафик идёт через `libp2p::noise::Config` — стандартный Noise IK. Сырой перехват пакетов на уровне TCP/QUIC даёт только зашифрованный шум. Это надёжно.

### E2EE чата (Double Ratchet)
Реализован в `src/crypto.rs`. Алгоритмы:

| Роль | Алгоритм |
|------|---------|
| DH-обмен | X25519 (`x25519-dalek`) |
| AEAD шифрование | ChaCha20-Poly1305 |
| KDF | BLAKE2b-512 (кастомная конструкция) |
| Out-of-order сообщения | `skipped_keys` — до 100 ключей |
| Очистка памяти | `Zeroize` / `ZeroizeOnDrop` на ключевых структурах |

Forward Secrecy и Post-Compromise Security обеспечиваются: компрометация одного ключа не раскрывает прошлые и будущие сообщения.

### Хранилище vault
`vault.bin` зашифрован AES-256-GCM с **случайным nonce** на каждое сохранение. Атомарная запись через `.tmp` + `rename` предотвращает порчу при сбое питания или краша.

## 2. Уязвимости и слабые места

### 🔴 КРИТИЧНО — первое сообщение уходит открытым текстом

**Файл:** `src/main.rs`, ~строка 1508  
**Описание:** Если E2EE сессия ещё не установлена (первый контакт), переменная `packet` остаётся `V1Packet::Plain(msg)`. Код отправляет `Hello` для инициации хендшейка, но *одновременно* отправляет и исходное сообщение в Plain-варианте.

```
let mut packet = V1Packet::Plain(msg.clone());  // по умолчанию Plain

if let Some(session) = sessions.get_mut(&peer_id) {
    packet = V1Packet::Encrypted { header, ciphertext };
} else {
    // сессии нет - Hello отправлен, но packet остался Plain!
    send_request(&peer_id, hello);
}
send_request(&peer_id, packet);  // уходит Plain
```

**Риск:** Тот, кто способен провести MITM на Noise-уровне (например, подменить bootstrap-ноду), читает первое сообщение открытым текстом.  
**Исправление:** Буферизовать сообщение до завершения E2EE хендшейка; отправлять только после получения ответного `Hello`.

### 🔴 КРИТИЧНО — нулевой nonce в каждом ChaCha20 шифровании

**Файл:** `src/crypto.rs`, строка 191  
**Описание:**

```
let nonce = Nonce::from_slice(&[0u8; 12]);  // всегда 0x000...000
let ciphertext = cipher.encrypt(nonce, plaintext)?;
```

Nonce жёстко захардкожен в нули для каждого сообщения. Безопасность ChaCha20-Poly1305 строится на уникальности пары `(key, nonce)`. Сейчас это держится только на уникальности `message_key`. Если в цепочке производства ключей когда-либо появится баг с повторением — одинаковые `(key=mk, nonce=0)` на двух открытых текстах раскрывают XOR обоих открытых текстов и ломают аутентификацию (GCM forgery).

**Риск:** Потенциально катастрофический при любой регрессии в KDF.  
**Исправление:** Использовать счётчик сообщений `ns` как nonce (`[0..8] = ns.to_le_bytes()`), либо генерировать случайный 12-байтовый nonce и передавать его вместе с шифртекстом.

### 🟠 ВЫСОКОЕ — `void.key` лежит на диске без пароля

**Файл:** `src/main.rs`, строки 312-323  
**Описание:**

```
fn get_master_key() -> [u8; 32] {
    if let Ok(k) = std::fs::read(Self::KEY_FILE) {
        // просто читает 32 сырых байта - никакого KDF, никакого пароля
        return key;
    }
    std::fs::write(Self::KEY_FILE, &key);  // пишет сырым
}
```

Ключ шифрования vault лежит в `void.key` в открытом виде рядом с `vault.bin`. Любой, кто имеет доступ к файловой системе (другой пользователь ОС, вредоносное ПО, утечка бэкапа), забирает оба файла и расшифровывает vault.

**Содержимое vault:**
- Статический X25519 секрет — весь архив переписки можно расшифровать ретроспективно
- libp2p keypair (Ed25519) — полный угон идентичности в сети

**Риск:** Полная компрометация при физическом доступе к устройству или заражении малварью.  
**Исправление:** Защитить `void.key` парольной фразой с KDF (Argon2id / scrypt / PBKDF2). Запрашивать пароль при запуске.

### ✅ ИСПРАВЛЕНО — `skipped_keys` не зероизировались

**Файл:** `src/crypto.rs`  
**Описание:**

Message keys для out-of-order сообщений хранились в `HashMap` с пометкой `#[zeroize(skip)]`. При уничтожении сессии через `Drop` они **не затирались** из RAM.

**Риск:** Дамп памяти процесса (crash dump, pagefile.sys/swap, cold-boot attack) содержит живые ключи сообщений.  
**Исправление применено:** Убраны derive-макросы `Zeroize`/`ZeroizeOnDrop` с `SecureSession`. Реализованы вручную:
- `impl Zeroize for SecureSession` — итерирует по всем значениям HashMap, зероизирует каждый ключ `[u8; 32]`, затем очищает карту; все остальные секретные поля обнуляются явно.
- `impl Drop for SecureSession` — вызывает `self.zeroize()`, гарантируя очистку при выходе из области видимости.

### 🟡 СРЕДНЕЕ — файлы не защищены E2EE

**Файл:** `src/file_transfer.rs`, `src/main.rs`  
**Описание:** Файловый протокол `/void/file/1.0.0` передаёт чанки как сырые байты. Double Ratchet на файлы не применяется — только Noise-транспорт.

**Риск:** Оператор relay-ноды, имеющий доступ к relay-процессу, видит содержимое передаваемых файлов в открытом виде (после декодирования транспортного шифрования изнутри процесса).  
**Исправление:** Шифровать файловые чанки тем же Double Ratchet сессионным ключом, что и текстовые сообщения, или отдельным согласованным симметричным ключом.

### 🟡 СРЕДНЕЕ — нестандартный KDF

**Файл:** `src/crypto.rs`, строки 14-22  
**Описание:**

```
fn kdf(salt: &[u8], ikm: &[u8], info: &[u8], output_len: usize) -> Vec<u8> {
    let mut hasher = Blake2b512::new();
    hasher.update(salt);   // конкатенация в одном хэше -
    hasher.update(ikm);    // не является стандартным HKDF
    hasher.update(info);
    result[..output_len].to_vec()
}
```

Это не HKDF, а самодельная конкатенация в BLAKE2b. Технически BLAKE2b устойчив к таким применениям, но конструкция не проходила независимый аудит. Стандарт Signal Protocol использует HKDF-SHA-256.

**Риск:** Низкий при текущем коде, но высокий при эволюции кодовой базы без понимания ограничений.  
**Исправление:** Заменить на `hkdf::Hkdf<Sha256>` или `hkdf::Hkdf<Blake2b512>` — стандартизированная, аудированная конструкция.

## 3. Итоговая таблица

| Слой | Алгоритм | Уровень защиты | Проблема |
|------|---------|---------------|---------|
| Транспорт (P2P) | Noise IK | **Высокий** | — |
| E2EE текст | Double Ratchet + ChaCha20-Poly1305 | **Средний** | Нулевой nonce; первое сообщение Plain |
| E2EE файлы | — (только Noise) | **Низкий** | Нет приложенческого шифрования |
| Локальный vault | AES-256-GCM | **Средний** | Ключ лежит рядом без пароля |
| Ключи в RAM | `zeroize` | **Средний** | `skipped_keys` не зероизируются |

## 4. Реальная вероятность перехвата

| Сценарий атаки | Шанс успеха | Обоснование |
|---------------|------------|------------|
| Пассивный перехват трафика (провайдер, DPI) | **~0%** | Noise шифрует весь транспорт |
| MITM на bootstrap/relay ноде (контроль узла) | **~30%** | Первое сообщение Plain, файлы не E2EE |
| Физический доступ к компьютеру жертвы | **~90%** | `void.key` читается открытым текстом |
| Malware с доступом к файловой системе | **~90%** | Те же файлы `void.key` + `vault.bin` |
| Дамп RAM работающего процесса | **~50%** | `skipped_keys` не зероизированы, текущие ключи в памяти |

## 5. Приоритет исправлений

| Приоритет | Проблема | Сложность исправления |
|----------|---------|----------------------|
| P0 | Первое сообщение — Plain | Средняя (буферизация до хендшейка) |
| P0 | Нулевой nonce в ChaCha20 | Низкая (использовать `ns` как nonce) |
| P1 | `void.key` без пароля | Средняя (добавить Argon2id) |
| P1 | `skipped_keys` не зероизируются | Низкая (убрать `#[zeroize(skip)]`) |
| P2 | Файлы не E2EE | Высокая (интеграция с Double Ratchet) |
| P3 | Нестандартный KDF | Низкая (заменить на HKDF) |

> Проект находится в стадии alpha и **не прошёл внешний аудит криптографии**.  
> Не используйте VOID для защиты жизни или свободы людей до устранения уязвимостей P0/P1.
