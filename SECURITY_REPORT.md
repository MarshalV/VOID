# Отчёт о безопасности VOID P2P Messenger

> Дата анализа: 27 апреля 2026  
> Проанализированные файлы: `src/crypto.rs`, `src/main.rs`, `src/file_transfer.rs`

---

## 1. Что защищено хорошо

### Транспортный уровень (Noise Protocol)
Весь P2P трафик идёт через `libp2p::noise::Config` — стандартный Noise IK. Сырой перехват пакетов на уровне TCP/QUIC даёт только зашифрованный шум. Это надёжно.

### E2EE чата (Double Ratchet)
Реализован в `src/crypto.rs`. Алгоритмы:

| Роль | Алгоритм |
|------|---------|
| DH-обмен | X25519 (`x25519-dalek`) |
| AEAD шифрование | ChaCha20-Poly1305 |
| KDF | HKDF-SHA256 ([RFC 5869](https://datatracker.ietf.org/doc/html/rfc5869)), `hkdf` + `sha2` |
| Out-of-order сообщения | `skipped_keys` — до 100 ключей |
| Очистка памяти | `Zeroize` / `ZeroizeOnDrop` на ключевых структурах |

Forward Secrecy и Post-Compromise Security обеспечиваются: компрометация одного ключа не раскрывает прошлые и будущие сообщения.

### Хранилище vault
`vault.bin` зашифрован AES-256-GCM с **случайным nonce** на каждое сохранение. Атомарная запись через `.tmp` + `rename` предотвращает порчу при сбое питания или краша.

## 2. Уязвимости и слабые места

### ✅ ИСПРАВЛЕНО — первое сообщение уходит открытым текстом

**Файл:** `src/main.rs`  
**Описание:** Если E2EE сессия ещё не установлена (первый контакт), переменная `packet` оставалась `V1Packet::Plain(msg)`. Код отправлял `Hello` для инициации хендшейка, но *одновременно* отправлял и исходное сообщение в Plain-варианте.

**Исправление (применено):** `V1Packet::Plain` полностью удалён из пути отправки. При отсутствии сессии сообщение помещается в `pending_messages: HashMap<PeerId, Vec<Vec<u8>>>`. После завершения хендшейка (во всех трёх ветках: Alice/Req, Bob/Res, Alice/Res) буфер флашится — каждое сообщение шифруется и отправляется уже как `V1Packet::Encrypted`. Повторный хендшейк не инициируется, если `pending_handshakes` уже содержит запись для пира.

---

### ✅ ИСПРАВЛЕНО — нулевой nonce в каждом ChaCha20 шифровании

**Файл:** `src/crypto.rs`  
**Описание:** Nonce был жёстко захардкожен в нули для каждого сообщения. Безопасность ChaCha20-Poly1305 строится на уникальности пары `(key, nonce)`. При любой регрессии в KDF повторение `message_key` с `nonce=0` раскрывало бы XOR обоих открытых текстов и ломало аутентификацию.

**Исправление (применено):** В `encrypt_payload` nonce формируется из счётчика отправки `ns` (значение до инкремента): первые 4 байта = `ns.to_le_bytes()`, остальные 8 = нули. В `decrypt_with_key` nonce восстанавливается из `header.n` (индекс сообщения, который совпадает с `ns` на момент шифрования). Это гарантирует уникальность nonce в рамках сессии без передачи дополнительных данных в пакете.

---

### ✅ ИСПРАВЛЕНО — `void.key` защищается паролем (Argon2id + AES-GCM)

**Файл:** `src/main.rs` (`Storage`: обёртка ключа, экран разблокировки перед сетью)  
**Было:** 32 сырых байта мастер-ключа в `void.key` без KDF; любой с копией `void.key` + `vault.bin` расшифровывал vault.

**Сейчас:**
- Файл `void.key` v2 начинается с магии `VOIDKEY2`, далее соль 32 байта, nonce 12 байт, AES-256-GCM шифротекст **мастер-ключа vault** (те же 32 байта, что и раньше шифровали `vault.bin`).
- Ключ для AES-обёртки выводится из пароля через **Argon2id** (`m=32768` KiB, `t=3`, `p=4`, выход 32 байта).
- При старте приложения показывается экран ввода пароля; **P2P-сеть не поднимается**, пока пароль не принят.
- Старый формат (ровно 32 байта без магии): при первом входе пользователь задаёт пароль, `void.key` перезаписывается в v2 без изменения уже зашифрованного `vault.bin`.

**Критичность данных:** после успешной расшифровки `vault.bin` злоумышленник получает и **долговременный X25519 секрет**, и **libp2p keypair** — то есть полную сетевую личность и возможность расшифровать протокольный трафик задним числом. Это не «ослабление» от Argon2, а описание того, что именно лежит внутри vault.

**Офлайн-атака:** при краже **обоих** файлов (`void.key` и `vault.bin`) перебор идёт по кандидатам парольной фразы: на каждый кандидат — вывод ключа Argon2id → попытка снять AES-обёртку с `void.key` → проверка расшифровки `vault.bin`. Argon2 повышает цену одной попытки, но не заменяет **достаточную энтропию** пароля (словарь и короткие фразы по-прежнему уязвимы к офлайн-подбору при наличии копий файлов).

**Резервные копии** нужны прежде всего, чтобы не потерять доступ при потере диска; храните их отдельно от основной машины и с тем же уровнем доверия, что и к живому профилю.

**Остаточный риск без перебора файлов:** разблокированная сессия, кейлоггер/троян с доступом к процессу, слабый пароль при вводе — типичные угрозы для любого локального хранилища секретов.

### ✅ ИСПРАВЛЕНО — `skipped_keys` не зероизировались

**Файл:** `src/crypto.rs`  
**Описание:**

Message keys для out-of-order сообщений хранились в `HashMap` с пометкой `#[zeroize(skip)]`. При уничтожении сессии через `Drop` они **не затирались** из RAM.

**Риск:** Дамп памяти процесса (crash dump, pagefile.sys/swap, cold-boot attack) содержит живые ключи сообщений.  
**Исправление применено:** Убраны derive-макросы `Zeroize`/`ZeroizeOnDrop` с `SecureSession`. Реализованы вручную:
- `impl Zeroize for SecureSession` — итерирует по всем значениям HashMap, зероизирует каждый ключ `[u8; 32]`, затем очищает карту; все остальные секретные поля обнуляются явно.
- `impl Drop for SecureSession` — вызывает `self.zeroize()`, гарантируя очистку при выходе из области видимости.

### ✅ ИСПРАВЛЕНО — файлы не защищены E2EE

**Файл:** `src/file_transfer.rs`, `src/main.rs`  
**Описание (было):** Файловый протокол `/void/file/1.0.0` передавал чанки как сырые байты. Double Ratchet на файлы не применялся — только Noise-транспорт.

**Риск (устранён для актуальной пары пиров):** Оператор relay-ноды с доступом к процессу relay видел бы содержимое чанков после декодирования транспорта.  

**Исправление применено:** Данные чанков кодируются бинарным фреймом `VfC1` и передаются как открытый текст внутри `V1Packet::Encrypted` по `/void/chat/1.0.0` — тем же `SecureSession::encrypt_payload` / `decrypt_payload` (Double Ratchet), что и обычные сообщения. Узлы согласованной версии больше не посылают полезную нагрузку файла по `FilePacket::Chunk`. Путь `Chunk` оставлен только для приёма от **устаревших** пиров; отправка файла без установленной E2EE-сессии блокируется.

---

### ✅ ИСПРАВЛЕНО — нестандартный KDF

**Файл:** `src/crypto.rs`  
**Описание (было):** Все производные ключи строились через конкатенацию `salt ‖ ikm ‖ info` в один проход BLAKE2b — не HKDF и не аудированная профильная схема.

**Исправление применено:** Добавлены зависимости `hkdf` и `sha2`; универсальная функция `hkdf_sha256_derive(salt, ikm, info, len)` выполняет **HKDF-SHA256** по [RFC 5869](https://datatracker.ietf.org/doc/html/rfc5869): `salt`/`ikm`/`info` сохранены по смыслу прежних аргументов (инициализация `rk`, шаг цепочки сообщений/chain key, `kdf_rk` при DH-ratchet).  

**⚠ Совместимость:** производные ключи **не совпадают** с прежней схемой BLAKE2b; между старым и новым билдом E2EE несовместим — нужен повторный хендшейк после обновления обоих пиров.

## 3. Итоговая таблица

| Слой | Алгоритм | Уровень защиты | Проблема |
|------|---------|---------------|---------|
| Транспорт (P2P) | Noise IK | **Высокий** | — |
| E2EE текст | Double Ratchet + ChaCha20-Poly1305 + HKDF-SHA256 | **Средний** | исторически нулевой nonce и Plain первого сообщения (исправлено в коде) |
| E2EE файлы | через тот же Double Ratchet (/void/chat) | **Средний** | метаданные оффера на /void/file всё ещё открыты для relay-слоя по сути контроля узла |
| Локальный vault | AES-256-GCM | **Средний** | Ключ лежит рядом без пароля |
| Ключи в RAM | ручной `Zeroize` для `SecureSession` | **Средний** | исторически `skipped_keys`; для актуальной сессии зероизируется |

## 4. Реальная вероятность перехвата

| Сценарий атаки | Шанс успеха | Обоснование |
|---------------|------------|------------|
| Пассивный перехват трафика (провайдер, DPI) | **~0%** | Noise шифрует весь транспорт |
| MITM на bootstrap/relay ноде (контроль узла) | **снижен** для полезной нагрузки | Plain-первое сообщение и plain-файловые чанки убраны в актуальной версии; метаданные оффера и видимость трафика на узле возможны при компрометации узла |
| Физический доступ при разблокированном приложении или известном пароле | **повышен** | Активная сессия: ключи в ОЗУ; только диск без пароля: нужен офлайн-брут `void.key`, а не простое чтение 32 байт |
| Malware при запущенном приложении | **повышен** | Может снять мастер-ключ после ввода пароля из памяти процесса; «только файлы» без пароля уже недостаточно для чтения `vault.bin` |
| Дамп RAM работающего процесса | **ущерб остаётся** | активные ключи в памяти; для `skipped_keys` зероизация включена при Drop сессии |

| P0 | Нулевой nonce в ChaCha20 | Низкая (использовать `ns` как nonce) |
| ~~P1~~ | ~~`void.key` без пароля~~ | Исправлено: Argon2id + AES-GCM обёртка, пароль при старте |
