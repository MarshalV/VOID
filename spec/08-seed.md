# 08. Seed диспетчеров

`/void-seed/v1` — не поток libp2p и не чат. Два диспетчера по отдельному TCP меняются списком публичных адресов. Участник этот порт не открывает и кадры seed не шлёт.

Первый адрес диспетчера участник узнаёт вне этого протокола (multiaddr с `/p2p/<PeerId>`). Дальше диспетчеры узнают друг друга сами.

Эталон: [MarshalV/bootstrap_node](https://github.com/MarshalV/bootstrap_node).

На сокете нет ни строки `/void-seed/v1`, ни `PeerId`. Оба появляются только внутри AEAD.

## Кадр

```
u32be(len) || body
```

`len` ≤ 1 МиБ. Больше — разрыв.

## Ключи сессии

Обе стороны дают эфемерный X25519: `e_c` (инициатор TCP), `e_s` (принявший).

```
DH = X25519(e_c, e_s)
okm = HKDF-SHA-512(
        salt = "/void-seed/v1" || e_c || e_s,
        ikm  = DH,
        info = "void-seed-session-keys",
        64)
k1 = okm[0..32]
k2 = okm[32..64]
```

Хеш HKDF — SHA-512, не Blake2. AAD каждого AEAD — ASCII `/void-seed/v1`. Nonce — 12 байт: первые 4 нуля, следующие 8 — счётчик little-endian `u64`. Тег ChaCha20-Poly1305 дописывается к шифртексту, отдельным полем не передаётся.

## Четыре сообщения

```
C → S   frame( e_c )                         ровно 32 байта тела
S → C   frame( e_s || AEAD(k1, n=0, auth_s) )
C → S   frame( AEAD(k2, n=0, auth_c || request) )
S → C   frame( AEAD(k2, n=1, response) )
```

`e_c` и `e_s` — 32 байта. После рукопожатия секреты эфемеров стираются.

Открытый текст — bincode 1.3 по умолчанию: little-endian, длина вектора и строки — `u64le`, имена полей не пишутся, порядок полей как ниже. Enum с внутренним тегом пишется как строка тега первым полем, затем поля варианта.

### `AuthPayload`

| Поле | Вид |
|------|-----|
| `static_ed_pub` | 32 байта Ed25519 |
| `peer_id_bytes` | байты `PeerId` |
| `libp2p_pubkey_proto` | protobuf ключа libp2p |
| `protocol_version` | строка, обязана быть `/void/v1` |
| `agent_version` | строка агента |
| `timestamp` | `u64` секунд Unix |
| `signature` | 64 байта |

Подпись Ed25519 на сообщении (не на всём `AuthPayload`):

```
"/void-seed/v1" || "|" || direction || "|" || e_c || e_s
```

`direction` — `s` у принявшего (msg2), `c` у инициатора (msg3). Вертикальная черта — один байт `0x7c`.

Проверка:

- `protocol_version` равен `/void/v1` (это метка внутри AEAD, не список допуска);
- `|now - timestamp| ≤ 300` секунд;
- подпись сходится с `static_ed_pub`;
- protobuf даёт тот же `PeerId`, что `peer_id_bytes`;
- Ed25519 внутри protobuf совпадает с `static_ed_pub`.

Чужой ключ не получит `k1`/`k2` и не подделает `auth`. Старый диспетчер с другим набором полей рукопожатие не заканчивает.

### Запрос и ответ

Запрос (`ClientMsg` = `auth`, затем `request`):

```
request = "exchange" || offer || want_max_u32
```

`offer` — вектор `SeedEntry`. Ответ:

```
"peers" || peers          # норма
"error" || message        # строка, список не принят
```

`SeedEntry` по порядку: `host` (строка), `seed_port` (`u16`), `libp2p_port` (`u16`), `peer_id_b58` (строка), `last_seen` (`u64`).

Это публичные адреса диспетчеров: куда открывать libp2p и куда открывать следующий seed. Секретов в записи нет. Принявший может запомнить наблюдённый адрес TCP; в кадр он его не кладёт, если сам не включил его в `SeedEntry`.

| Наблюдатель | Видит | Не видит |
|-------------|-------|----------|
| Пассивный на TCP | длину кадров и 32 случайных байта `e_c` в первом теле; дальше шифртекст | `/void/v1`, `PeerId`, список, порты |
| Диспетчер-сторона | после AEAD — `PeerId` соседа, подпись, список `SeedEntry` | долговременный секрет чужого ключа; эфемеры после сессии |
| Участник чата | ничего этого потока | список seed, если ему его не отдали отдельно как multiaddr |
