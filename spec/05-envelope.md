# 05. Конверт, prekey, ящик

Живой путь — request-response на `/void/chat/1.0.0` к диспетчеру. DHT не второй ящик по PeerId: новый `put` на `/void/mailbox/` не принимается. Диспетчер конверт не открывает.

Участник, который уже знает диспетчера, шлёт `Store` только диспетчерам. Чужой `Store` он не хранит и отвечает пустым `Deliver` (отказ). Участник без единого диспетчера применяет те же правила к соседям, но держит не больше 256 ящиков.

## Prekey

Срок signed-prekey — 7 суток. Когда до `not_after` осталось меньше 24 часов, владелец меняет ключ. Предыдущий секрет хранит до его `not_after`, затем стирает. Рядом владелец держит пул из 16 одноразовых X25519 и отдаёт его диспетчеру в `PrekeyPut`. В значение DHT prekey этот пул не входит, и отдельный `/void/opk/<peer>` не пишется. Одноразовый ключ стирается после open; тот же id второй конверт не открывает.

Чем закрывается новое письмо, решает `PrekeyOffer`. Подписанный prekey можно прочитать и из DHT:

1. Есть signed-prekey и один одноразовый — два DH, соль `VOID_OFFLINE_X3DH`. `opk_id` (16 байт) входит в подпись, в поля внутри `ct` и в AAD.
2. Есть только signed-prekey, и у него ключ ML-KEM-768 — один DH и секрет KEM, соль `VOID_OFFLINE_PQ`. В начало `ct` пишутся `VQK1` и ciphertext KEM (1088 байт), затем AEAD. Поля конверта те же.
3. Есть только signed-prekey без ключа KEM — один DH, соль `VOID_OFFLINE_V2`.
4. Sealable prekey нет — конверт не создаётся, письмо остаётся в `outbox.bin`. X25519 из `PeerId` ([01-identity.md](01-identity.md)) новое письмо не запечатывает. Им открываются уже закрытые на него старые конверты.

Диспетчер хранит пул в `node_prekeys.bin`. `PrekeyGet` отдаёт один ключ и стирает его до ответа. Путь 1 срабатывает, когда Offer его вернул. Старая запись `/void/opk/`, если она ещё лежит, доживает свой TTL.

### Подпись v2

```
"VOID_PREKEY_SIG_V2\0"
|| u32le(len(owner.to_bytes())) || owner.to_bytes()
|| pk[32]
|| not_after_le_u64
```

Подпись транспорта владельца. Старая v1 без срока:

```
"VOID_PREKEY_SIG_V1\0" || u32le(len(owner)) || owner.to_bytes() || pk[32]
```

v1 ещё проверяется и для запечатывания не годится.

### Подпись v3

Когда рядом с X25519 лежит ключ инкапсуляции ML-KEM-768 (1184 байта):

```
"VOID_PREKEY_SIG_V3\0"
|| u32le(len(owner.to_bytes())) || owner.to_bytes()
|| pk[32]
|| not_after_le_u64
|| kem_ek[1184]
```

### Одноразовый ключ

```
"VOID_OPK_SIG_V1\0"
|| u32le(len(owner.to_bytes())) || owner.to_bytes()
|| id[16]
|| pk[32]
```

Нулевой `id` или нулевой `pk` не подписывают. Форма старой записи DHT `/void/opk/<owner>`, новый `put` которой не принимается:

```
0x01 || u16le(count) || (id[16] || pk[32] || u32le(len(sig)) || sig)*
```

`count` от 1 до 16. Чужая подпись в списке — вся запись отвергается.

### `PrekeyPut` / `PrekeyGet` / `PrekeyOffer`

JSON или CBOR на `/void/chat/1.0.0` (когда писать CBOR — [02-hello.md](02-hello.md)):

```
PrekeyPut   { peer_id, public_key[32], not_after, sig, opks, kem_ek }
PrekeyGet   { peer_id }
PrekeyOffer { peer_id, public_key[32], not_after, sig, opk, kem_ek }
```

`sig` — сырые байты подписи v2 или v3, не DHT-блоб. `kem_ek` пуст у записи v2 и равен 1184 байтам у v3. `opks` — список одноразовых (`id`, `pk`, `sig`). `opk` в Offer — один такой ключ или пусто. Иная длина `kem_ek` запись отвергает.

Диспетчер на `PrekeyPut`:

1. Noise-`PeerId` соединения равен `peer_id`. Иначе не хранить.
2. `public_key` не из нулей, `sig` не пуста, `not_after > now` и `not_after ≤ now + 30 суток`.
3. `kem_ek` пуст — подпись v2. `kem_ek` ровно 1184 байта — подпись v3. Ключ — identity внутри этого `PeerId`.
4. Успех — запомнить `(pk, not_after, sig, kem_ek)` и список `opks` (не больше 16) и ответить `Ack`. Запись лежит в `node_prekeys.bin` и переживает рестарт. Уже выданный id в пул не возвращается.
5. Любой провал — ничего не менять и всё равно ответить `Ack`, чтобы запрос завершился. Следующий `Get` будет промахом.

`PrekeyGet`: если запись годится для печати и в пуле есть одноразовый ключ — `PrekeyOffer` с `public_key`, `not_after`, `sig`, `kem_ek` и одним `opk`. Этот ключ стирается, файл сохраняется до ответа. Второй `Get` этот id не получает. Пустой пул — `Ack`. Просроченный signed-prekey стирает и остаток пула, ответ тоже `Ack`. Непрошеный `Offer` получатель игнорирует. `Offer` используется для печати только если подпись и срок сходятся и это ответ на свой `Get`.

Запись в DHT — другой код тех же полей, см. ниже и [06-discovery.md](06-discovery.md).

## Конверт v3

Отправитель обязан слать v3. Приёмник обязан открывать v3 и может открывать v2. v1 (без подписи) отвергается.

Внешний объект (JSON в `Store`/`Deliver`, bincode в DHT):

| Поле | v3 на проводе |
|------|----------------|
| `v` | `3` |
| `sender` | `""` |
| `sender_pk` | 32 нуля |
| `message_id` | 32 hex, внешний id |
| `kind` | `""` |
| `eph` | 32 байта, эфемерный X25519, не нули |
| `nonce` | 12 байт |
| `ct` | шифр, 1 .. 65536 байт в DHT-записи. Гибридное письмо начинается с `VQK1` |

`local_kind` на провод не сериализуется.

Внешний id, 16 байт в hex:

```
SHA-256( "VOID_OFFLINE_ID_V3\0" || recipient.to_bytes() || message_id_utf8 )[0..16]
```

Один и тот же внутренний id у двух получателей даёт два внешних id. Повтор того же письма тому же получателю даёт тот же внешний id — по нему диспетчер схлопывает дубликат и не видит настоящий id (`vchunk:…` и любой другой).

### Ключ AEAD

Один DH, `recipient_pk` — signed-prekey. X25519 из `PeerId` в этой формуле остаётся только у конверта, который уже был закрыт на него:

```
key = HKDF-SHA256("VOID_OFFLINE_V2", DH, "mail" || eph || recipient_pk, 32)
```

Два DH, когда есть одноразовый ключ. KEM сюда не подмешивается:

```
ikm = DH(eph, signed-prekey) || DH(eph, OPK)
key = HKDF-SHA256("VOID_OFFLINE_X3DH", ikm,
                  "mail" || eph || spk || opk_id || opk_pk, 32)
```

Один DH и ML-KEM-768, когда одноразового нет, а `kem_ek` есть. Отправитель делает Encaps, получатель — Decaps тем же ключом:

```
ikm = DH(eph, signed-prekey) || kem_ss
key = HKDF-SHA256("VOID_OFFLINE_PQ", ikm, "mail" || eph || recipient_pk, 32)
ct  = "VQK1" || kem_ct[1088] || aead
```

`kem_ss` — 32 байта. AAD у такого письма — обычный AAD v3, без `opk_id`. Получатель сначала пробует открыть весь `ct` ключом одного DH. Не вышло и в начале стоят байты `VQK1` — снимает KEM и пробует ключ выше.

### AAD v3

```
"VOID_OFFLINE_AAD_V3\0" || 0x03
|| u32le(len(recipient.to_bytes())) || recipient.to_bytes()
|| u32le(len(outer_id_utf8)) || outer_id_utf8
|| eph
```

Смена внешнего id или получателя ломает тег.

### Что внутри `ct`

Открытый текст AEAD:

```
u16le(len(sig)) || sig || u16le(len(pubkey_pb)) || pubkey_pb || fields_padded
```

`sig` 1..256, `pubkey_pb` 0..4096 (пусто, если ключ уже в identity-`PeerId`).

`fields` до дополнения:

```
u32le(len(sender.to_bytes())) || sender.to_bytes()
|| sender_pk[32]
|| u32le(len(message_id)) || message_id          # 1..1024
|| u32le(len(kind)) || kind                      # 1..64
|| u32le(len(body)) || body
```

Дополнение нулями до `padded_len(|fields|)`:

```
если n ≤ 4096:  next_power_of_two(max(n, 512))
иначе:          ceil(n / 4096) * 4096
```

Подпись транспорта отправителя покрывает не дополненный блоб, а

```
header || SHA-256(body)
```

`body` — исходные байты письма, без длины и без нулей дополнения. `header`:

```
"VOID_OFFLINE_SIG_V3\0" || 0x03
|| lp(sender) || lp(recipient) || sender_pk
|| lp(message_id) || lp(kind) || eph
```

`lp(x)` = `u32le(len)` || байты. Для `PeerId` байты — `to_bytes()`. Получатель проверяет, что внешний id совпал с формулой, и только потом подпись.

Письмо с одноразовым ключом вставляет `opk_id` (16 байт, без длины) в три места: в конец `header` подписи, в `fields` сразу после `lp(kind)` и до `lp(body)`, и в конец AAD v3. Нулевой `opk_id` такое письмо не запечатывает.

Внутренние `kind`, которые участник понимает:

| `kind` | `body` |
|--------|--------|
| `dm`, `group` | JSON сообщения чата. `sender_id` в JSON обязан совпасть с подписавшим `PeerId` |
| `group_sync` | JSON `group_sync` ([10-groups.md](10-groups.md)); автор подписи — отправитель конверта |
| `voice_chunk` | см. ниже |
| `file_chunk` | то же тело, что у `voice_chunk` |

Иной `kind` получатель может отбросить. Диспетчер `kind` не видит.

### `voice_chunk`

Внутренний `message_id` произвольный (участники сходятся на повторе сами). Тело:

```
transfer_id[16] || index_le_u32 || total_le_u32 || total_size_le_u32 || data
```

`total ≥ 1`, `index < total`, `data` до 24 КиБ. Собранные байты не больше 3 МиБ. Это сжатый голос (`VVAD`), не длиннее 60 секунд. Сборка: все индексы `0..total-1`, длина равна `total_size`. После этого получатель возвращает WAV. Отдельного хэша у куска нет. JSON с `duration_secs` больше 60 получатель отбрасывает. Крупнее в офлайн-очередь не режется. Это всё ещё внутри `ct`.

### `file_chunk`

То же тело и тот же потолок куска, что у `voice_chunk`. Участник читает исходник до 64 МиБ и кладёт в очередь сжатый файл (`VZDF`), если он короче исходного и не больше 8 МиБ. Это около 350 писем, каждое занимает полный бакет очереди 64 КиБ, и одна передача не забирает всю квоту очереди (1024 письма). Крупнее остаётся на живом `VfC1`. Рядом идёт обычное `dm` или `group` с `file`: имя, размер и 64 hex BLAKE2b (первые 32 байта) сжатых байт. Получатель собирает куски, сверяет хэш сжатых байт, разжимает и только потом пишет файл. Байты файла в DHT не кладутся.

### Конверт v2

Только приём. Снаружи `sender` (base58), `sender_pk`, `message_id`, `kind` заполнены. AAD и подпись — те же поля с префиксами `VOID_OFFLINE_AAD_V2\0` и `VOID_OFFLINE_SIG_V2\0` и байтом версии `2`, без внешнего id. Внутри `ct` сразу `sig || pubkey_pb || body` (u16-длины), без спрятанных полей и без бакета. Новый код так не шлёт: диспетчер v3 видит отправителя, если принять v2 в ящик. Диспетчер v3-ящика такой конверт не хранит.

## Что делает диспетчер

Поле кадра, до ящика: один `Store` несёт не больше 64 конвертов. `ct` каждого конверта и `Onion.ct` — не длиннее 256 КиБ, `Encrypted.ciphertext` — не длиннее 1 МиБ. `Deliver` — не больше 1024 конвертов. Это потолок разбора, не правило слота. Участник часто шлёт по одному конверту.

Основной ящик — очередь контакта. Слот PeerId принимает `OfflineMailboxStore`, который всё ещё пришёл.

### `OfflineMailboxStore { recipient, envelopes }`

Эталонный диспетчер кладёт это в слот PeerId. Имя слота — `mailbox_slot` от строки `recipient`. `PeerId` загрузившего не пишется.

1. Пустой `recipient` или пустой список — ничего не писать, ответ `OfflineMailboxDeliver` с пустым списком.
2. Новый слот при уже занятых 4096 слотах не создавать: тот же пустой `Deliver`.
3. Конверт с тем же внешним `message_id` пропустить.
4. В слоте не больше 1024 конвертов и 32 МиБ. Лишнее снимается с головы.
5. Конверт живёт 7 суток с момента приёма. Просроченное стирается и в выдачу не попадает.
6. Запись состоялась — `Ack`. Иначе пустой `Deliver`.

`Ack` значит «диспетчер принял ответственность». Пустой `Deliver` на `Store` значит «не принял, отправитель оставляет письмо у себя и повторит». Это не выдача почты.

Диспетчер не смотрит внутрь `ct`, не проверяет подпись отправителя и не узнаёт `kind`. Снаружи v3 он тоже не требует. Квоты «600 запросов за 60 секунд, 256 конвертов и 8 МиБ от одного загрузившего, `ct` ≤ 64 КиБ» у этого слота нет. Их по-прежнему проверяет память `protocol-conformance`, не бинарь `void-bootstrap-node`.

### `OfflineMailboxQuery { recipient }`

Слот PeerId выдаётся, когда `recipient` разбирается в тот же `PeerId`, что Noise этого соединения. Иначе `Ack`, слот не трогать. Чужому слоту не подтверждают, что он непуст. Через выход луковицы предыдущий hop владельцем не считается, и слот оттуда не выдаётся.

1. Свой слот: забрать пачку с головы. Объём конверта — `|ct| + 96`. Первый берётся всегда, даже если он один больше лимита. Следующий не берётся, если сумма превысит 512 КиБ.
2. Взятые конверты стираются до отправки ответа. Пустой слот удаляется.
3. Пачка пустая — `Ack`. Иначе `OfflineMailboxDeliver { envelopes }`.

Диспетчер не толкает почту сам. Клиент шлёт этот `Query`, как только TCP до диспетчера есть, и дальше примерно раз в секунду. Поля `ts`, `nonce` и `sig` он не пишет, пока они нулевые.

`MailboxChallengeRequest` эталонный диспетчер не разбирает. Кадр крейта, который нода не обслуживает, закрывает запрос и не отвечает `Ack`: тихий `Ack` клиент уже принимает за сдачу письма. `Hello` только запоминает бит CBOR. Входная ячейка луковицы по-прежнему отвечает коротким `Ack`: ячейка принята, письмо не записано. Сообщение подписи, которое проверяет участник без диспетчера и `protocol-conformance`:

```
"VOID_MAILBOX_QUERY_v1" || recipient.to_bytes() || ts_le || nonce[32]
```

Nonce одноразовый, `ts` внутри ±2 минут, ключ — тот, чей `PeerId` равен `recipient`. Участник в LAN без диспетчера выдаёт nonce и отдаёт ящик только после этой подписи. Опрос клиента шлёт нулевые поля: это сходится с диспетчером и не проходит проверку LAN.

`Ack` входного hop значит «ячейка принята», не «конверт записан». Запись и выдача через луковицу — в [09-onion.md](09-onion.md).

### Очередь контакта

Это ящик, который читает получатель, когда грант жив. Владелец очереди — свежий Ed25519, не PeerId получателя. `queue_id` и `write_token` — по 32 случайных байта. Срок — не дальше 14 суток от `now`. `CreateQueue`:

```
queue_id[32], owner_pk, write_token[32], expiry, sig
```

`owner_pk` — protobuf этого Ed25519. Подпись покрывает

```
"VOID_QUEUE_CREATE_V1\0" || queue_id || write_token || expiry_le
```

`expiry > now` и не дальше 14 суток. Подпись и срок не сошлись — пустой `QueueDeliver`. Иначе `Ack`. Грант `(queue_id, write_token, expiry)` уходит отправителю внутри E2EE и только после Hello с битом `4`. `QueueStore`:

```
queue_id[32], proof[32], blob
```

`blob` — ровно 64 КиБ: `u32le` длины bincode-конверта, сам конверт, хвост нулями. Иная длина — отказ. `proof` проверяется до записи. Это SHA-256 от

```
"VOID_QUEUE_WRITE_V1\0" || write_token || queue_id || blob
```

Перед запросом владелец шлёт `QueueChallengeRequest { queue_id }`. Диспетчер отвечает `QueueChallenge { nonce, ts }` или `Ack`, если очереди нет. `QueueQuery` подписывает тот же ключ владельца:

```
"VOID_QUEUE_QUERY_V1\0" || queue_id || ts_le || nonce[32]
```

Запись и повтор того же блоба — `Ack`. Отказ — пустой `QueueDeliver`. В одной очереди не больше 1024 блобов и 64 МиБ. Полная очередь снимает самый старый блоб, если после этого новый влезает. Новый `queue_id` сверх 4096 очередей не создаётся. Уже существующая очередь запись принимает. Срок проверяется на записи, на выдаче и раз в 90 секунд.

Клиент с живым грантом и TCP до диспетчера шлёт только `QueueStore` и ждёт `Ack` на этот запрос. Копию `OfflineMailboxStore` тогда не шлёт. Гранта нет, TCP нет или `QueueStore` не собрался — уходит слот PeerId. Пока TCP нет, но есть вход луковицы, клиент тоже шлёт слот PeerId: очередь в ячейку он не кладёт.

`QueueQuery` отдаёт пачку только после подписи владельца. Проверка снаружи функции, которая снимает пачку. Отказ и пустая пачка — `Ack`. Непустая — `QueueDeliver`. Если ответ луковицы не собрался, снятая пачка возвращается.

После 64 записей или когда до `expiry` меньше суток владелец заводит новую очередь. Старый `queue_id` выдаётся до своего `expiry`. В журнале `info` строка `queue=` и первые 8 байт id в hex, затем `bucket=65536`. Получателя и TCP-пира в ней нет.

### Что участник делает с `Deliver`

Открывает текущим signed-prekey, предыдущим, оставшимися одноразовыми и X25519 из своего `PeerId`. Письмо с `VQK1` открывается ещё и секретом ML-KEM этого prekey. Письмо с `opk_id` открывается парой signed-prekey и этого одноразового, после чего одноразовый стирается. Чужая сторона, подмена `ct`, чужой `recipient` в AAD, v1 — выброс. Для `dm` и `group` сверяет `sender_id` с подписавшим.

## DHT-значение ящика

Ключ: байты `"/void/mailbox/"` || `recipient.to_bytes()`.

Значение — bincode 1.3 (little-endian, длины по 8 байт, без имён полей) непустого списка тех же объектов, что и JSON-конверт. Порядок полей: `v`, `sender`, `sender_pk`, `message_id`, `kind`, `eph`, `nonce`, `ct`. Весь блоб ≤ 64 КиБ, в списке ≤ 64 конвертов. Читатель может принять старый JSON-массив той же формы. Писатель новых записей шлёт bincode. Срок записи — 7 суток. Проверка формы — та же, что у `dht_record_allowed` для ключа `/void/mailbox/`. Пока очередь включена, новый `put` этого ключа не принимается и участник его не шлёт. Уже записанное доживает эти 7 суток. Ключа `/void/queue/` нет ([06-discovery.md](06-discovery.md)).

DHT-значение prekey, ключ `"/void/prekey/"` || `owner.to_bytes()`:

v2:

```
pk[32] || 0x02 || not_after_le_u64
|| u16le(len(sig)) || sig || u16le(len(pubkey_pb)) || pubkey_pb
```

v3, ключ инкапсуляции сразу после срока:

```
pk[32] || 0x03 || not_after_le_u64 || kem_ek[1184]
|| u16le(len(sig)) || sig || u16le(len(pubkey_pb)) || pubkey_pb
```

Хвоста после `pubkey_pb` нет. Узел кладёт запись, только если подпись этой версии сошлась и срок годится для печати (`now < not_after ≤ now + 30 суток`). Метку `0x02` проверяют раньше `0x03`. v1 (нет метки) подпись может подтвердить, в хранилище её не кладут.

| Наблюдатель | Видит | Не видит |
|-------------|-------|----------|
| Диспетчер ящика | у слота PeerId — `recipient`, внешний `message_id`, размер и время приёма. Загрузившего там нет. У очереди — короткий id и бакет 64 КиБ | отправителя, настоящий id, `kind`, тело |
| Владелец на `Query` | пачку своих конвертов; после вскрытия — подписавшего и `kind` | конверты, которые диспетчер ещё не отдал (они стёрты только у него в этой пачке) |
| Чужой участник, сделавший `Query` | ответ `Ack` | есть ли ящик и что в нём |
| Узел DHT | подписанный prekey. Старый `/void/mailbox/` может ещё лежать до своего TTL | новый `put` ящика и одноразовый ключ: оба отвергаются. Внутри `ct` — то же, чего не видит диспетчер |
| Загрузивший | `Ack` (принято) или пустой `Deliver` (отказ) | чужие конверты в этом ящике |
