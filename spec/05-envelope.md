# 05. Конверт, prekey, ящик

Живой путь — request-response на `/void/chat/1.0.0` к диспетчеру. DHT — запасной слот тех же байтов, не основной путь доставки. Диспетчер конверт не открывает.

Участник, который уже знает диспетчера, шлёт `Store` только диспетчерам. Чужой `Store` он не хранит и отвечает пустым `Deliver` (отказ). Участник без единого диспетчера применяет те же правила к соседям, но держит не больше 256 ящиков.

## Prekey

Срок signed-prekey — 7 суток. Когда до `not_after` осталось меньше 24 часов, владелец меняет ключ. Предыдущий секрет хранит до его `not_after`, затем стирает. Рядом владелец держит пул из 16 одноразовых X25519 и публикует его в DHT `/void/opk/<peer>`. Одноразовый ключ стирается после open; тот же id второй конверт не открывает.

Чем закрывается новое письмо, решает то, что вернул `PrekeyOffer` или DHT:

1. Есть signed-prekey и один одноразовый — два DH, соль `VOID_OFFLINE_X3DH`. `opk_id` (16 байт) входит в подпись, в поля внутри `ct` и в AAD.
2. Есть только signed-prekey, и у него ключ ML-KEM-768 — один DH и секрет KEM, соль `VOID_OFFLINE_PQ`. В начало `ct` пишутся `VQK1` и ciphertext KEM (1088 байт), затем AEAD. Поля конверта те же.
3. Есть только signed-prekey без ключа KEM — один DH, соль `VOID_OFFLINE_V2`.
4. Sealable prekey нет — тот же один DH на X25519 из `PeerId` ([01-identity.md](01-identity.md)), и письмо всё равно уходит в ящик. Этот ключ открывает и старые конверты, закрытые на него.

Диспетчер этого дерева одноразовые ключи не хранит и в `PrekeyOffer` не кладёт. Пока Offer такой, живое письмо идёт путём 2, 3 или 4. Путь 1 срабатывает, когда одноразовый ключ есть в ответе или в DHT.

### Подпись v2

```
"VOID_PREKEY_SIG_V2\0"
|| u32le(len(owner.to_bytes())) || owner.to_bytes()
|| pk[32]
|| not_after_le_u64
```

Подпись транспорта владельца. Старая v1 без срока:

```
"VOID_PREKEY_SIG_V1\0" || u32le(len(owner)) || owner.to_bytes() || pk[32]
```

v1 ещё проверяется и для запечатывания не годится.

### Подпись v3

Когда рядом с X25519 лежит ключ инкапсуляции ML-KEM-768 (1184 байта):

```
"VOID_PREKEY_SIG_V3\0"
|| u32le(len(owner.to_bytes())) || owner.to_bytes()
|| pk[32]
|| not_after_le_u64
|| kem_ek[1184]
```

### Одноразовый ключ

```
"VOID_OPK_SIG_V1\0"
|| u32le(len(owner.to_bytes())) || owner.to_bytes()
|| id[16]
|| pk[32]
```

Нулевой `id` или нулевой `pk` не подписывают. В DHT `/void/opk/<owner>`:

```
0x01 || u16le(count) || (id[16] || pk[32] || u32le(len(sig)) || sig)*
```

`count` от 1 до 16. Чужая подпись в списке — вся запись отвергается.

### `PrekeyPut` / `PrekeyGet` / `PrekeyOffer`

JSON или CBOR на `/void/chat/1.0.0` (когда писать CBOR — [02-hello.md](02-hello.md)):

```
PrekeyPut   { peer_id, public_key[32], not_after, sig, opks, kem_ek }
PrekeyGet   { peer_id }
PrekeyOffer { peer_id, public_key[32], not_after, sig, opk, kem_ek }
```

`sig` — сырые байты подписи v2 или v3, не DHT-блоб. `kem_ek` пуст у записи v2 и равен 1184 байтам у v3. `opks` — список одноразовых (`id`, `pk`, `sig`). `opk` в Offer — один такой ключ или пусто. Иная длина `kem_ek` запись отвергает.

Диспетчер на `PrekeyPut`:

1. Noise-`PeerId` соединения равен `peer_id`. Иначе не хранить.
2. `public_key` не из нулей, `sig` не пуста, `not_after > now` и `not_after ≤ now + 30 суток`.
3. `kem_ek` пуст — подпись v2. `kem_ek` ровно 1184 байта — подпись v3. Ключ — identity внутри этого `PeerId`.
4. Успех — запомнить `(pk, not_after, sig, kem_ek)` и ответить `Ack`. Список `opks` диспетчер этого дерева не хранит.
5. Любой провал — ничего не менять и всё равно ответить `Ack`, чтобы запрос завершился. Следующий `Get` будет промахом.

`PrekeyGet`: если запись ещё годится для печати — `PrekeyOffer` с `public_key`, `not_after`, `sig` и `kem_ek`. Одноразового ключа в ответе диспетчера этого дерева нет. Иначе `Ack`. Непрошеный `Offer` получатель игнорирует. `Offer` используется для печати только если подпись и срок сходятся и это ответ на свой `Get`.

Запись в DHT — другой код тех же полей, см. ниже и [06-discovery.md](06-discovery.md).

## Конверт v3

Отправитель обязан слать v3. Приёмник обязан открывать v3 и может открывать v2. v1 (без подписи) отвергается.

Внешний объект (JSON в `Store`/`Deliver`, bincode в DHT):

| Поле | v3 на проводе |
|------|----------------|
| `v` | `3` |
| `sender` | `""` |
| `sender_pk` | 32 нуля |
| `message_id` | 32 hex, внешний id |
| `kind` | `""` |
| `eph` | 32 байта, эфемерный X25519, не нули |
| `nonce` | 12 байт |
| `ct` | шифр, 1 .. 65536 байт в DHT-записи. Гибридное письмо начинается с `VQK1` |

`local_kind` на провод не сериализуется.

Внешний id, 16 байт в hex:

```
SHA-256( "VOID_OFFLINE_ID_V3\0" || recipient.to_bytes() || message_id_utf8 )[0..16]
```

Один и тот же внутренний id у двух получателей даёт два внешних id. Повтор того же письма тому же получателю даёт тот же внешний id — по нему диспетчер схлопывает дубликат и не видит настоящий id (`vchunk:…` и любой другой).

### Ключ AEAD

Один DH, `recipient_pk` — signed-prekey или X25519 из `PeerId`:

```
key = HKDF-SHA256("VOID_OFFLINE_V2", DH, "mail" || eph || recipient_pk, 32)
```

Два DH, когда есть одноразовый ключ. KEM сюда не подмешивается:

```
ikm = DH(eph, signed-prekey) || DH(eph, OPK)
key = HKDF-SHA256("VOID_OFFLINE_X3DH", ikm,
                  "mail" || eph || spk || opk_id || opk_pk, 32)
```

Один DH и ML-KEM-768, когда одноразового нет, а `kem_ek` есть. Отправитель делает Encaps, получатель — Decaps тем же ключом:

```
ikm = DH(eph, signed-prekey) || kem_ss
key = HKDF-SHA256("VOID_OFFLINE_PQ", ikm, "mail" || eph || recipient_pk, 32)
ct  = "VQK1" || kem_ct[1088] || aead
```

`kem_ss` — 32 байта. AAD у такого письма — обычный AAD v3, без `opk_id`. Получатель сначала пробует открыть весь `ct` ключом одного DH. Не вышло и в начале стоят байты `VQK1` — снимает KEM и пробует ключ выше.

### AAD v3

```
"VOID_OFFLINE_AAD_V3\0" || 0x03
|| u32le(len(recipient.to_bytes())) || recipient.to_bytes()
|| u32le(len(outer_id_utf8)) || outer_id_utf8
|| eph
```

Смена внешнего id или получателя ломает тег.

### Что внутри `ct`

Открытый текст AEAD:

```
u16le(len(sig)) || sig || u16le(len(pubkey_pb)) || pubkey_pb || fields_padded
```

`sig` 1..256, `pubkey_pb` 0..4096 (пусто, если ключ уже в identity-`PeerId`).

`fields` до дополнения:

```
u32le(len(sender.to_bytes())) || sender.to_bytes()
|| sender_pk[32]
|| u32le(len(message_id)) || message_id          # 1..1024
|| u32le(len(kind)) || kind                      # 1..64
|| u32le(len(body)) || body
```

Дополнение нулями до `padded_len(|fields|)`:

```
если n ≤ 4096:  next_power_of_two(max(n, 512))
иначе:          ceil(n / 4096) * 4096
```

Подпись транспорта отправителя покрывает не дополненный блоб, а

```
header || SHA-256(body)
```

`body` — исходные байты письма, без длины и без нулей дополнения. `header`:

```
"VOID_OFFLINE_SIG_V3\0" || 0x03
|| lp(sender) || lp(recipient) || sender_pk
|| lp(message_id) || lp(kind) || eph
```

`lp(x)` = `u32le(len)` || байты. Для `PeerId` байты — `to_bytes()`. Получатель проверяет, что внешний id совпал с формулой, и только потом подпись.

Письмо с одноразовым ключом вставляет `opk_id` (16 байт, без длины) в три места: в конец `header` подписи, в `fields` сразу после `lp(kind)` и до `lp(body)`, и в конец AAD v3. Нулевой `opk_id` такое письмо не запечатывает.

Внутренние `kind`, которые участник понимает:

| `kind` | `body` |
|--------|--------|
| `dm`, `group` | JSON сообщения чата. `sender_id` в JSON обязан совпасть с подписавшим `PeerId` |
| `group_sync` | JSON `group_sync` ([10-groups.md](10-groups.md)); автор подписи — отправитель конверта |
| `voice_chunk` | см. ниже |
| `file_chunk` | то же тело, что у `voice_chunk` |

Иной `kind` получатель может отбросить. Диспетчер `kind` не видит.

### `voice_chunk`

Внутренний `message_id` произвольный (участники сходятся на повторе сами). Тело:

```
transfer_id[16] || index_le_u32 || total_le_u32 || total_size_le_u32 || data
```

`total ≥ 1`, `index < total`, `data` до 24 КиБ. Собранные байты не больше 3 МиБ. Это сжатый голос (`VVAD`), не длиннее 60 секунд; получатель возвращает из него WAV. Крупнее в офлайн-очередь не режется. Сборка: все индексы `0..total-1`, длина равна `total_size`. Это всё ещё внутри `ct`.

### `file_chunk`

То же тело и тот же потолок куска, что у `voice_chunk`. В очередь кладётся сжатый файл (`VZDF`), если он короче исходного, и не больше 8 МиБ. Это около 350 писем, каждое занимает полный бакет очереди 64 КиБ, и одна передача не забирает всю квоту очереди (1024 письма). Крупнее остаётся на живом `VfC1`. Рядом идёт обычное `dm` или `group` с `file`: имя, размер и 64 hex BLAKE2b (первые 32 байта) сжатых байт. Получатель собирает куски, сверяет хэш, разжимает и только потом пишет файл. Байты файла в DHT не кладутся.

### Конверт v2

Только приём. Снаружи `sender` (base58), `sender_pk`, `message_id`, `kind` заполнены. AAD и подпись — те же поля с префиксами `VOID_OFFLINE_AAD_V2\0` и `VOID_OFFLINE_SIG_V2\0` и байтом версии `2`, без внешнего id. Внутри `ct` сразу `sig || pubkey_pb || body` (u16-длины), без спрятанных полей и без бакета. Новый код так не шлёт: диспетчер v3 видит отправителя, если принять v2 в ящик. Диспетчер v3-ящика такой конверт не хранит.

## Что делает диспетчер

Объём конверта для квот: `|ct| + 96`.

Один `Store` несёт не больше 64 конвертов. `ct` каждого конверта и `Onion.ct` — не длиннее 256 КиБ, `Encrypted.ciphertext` — не длиннее 1 МиБ. Это потолок поля, не всего JSON. `Deliver` — не больше 1024 конвертов с тем же потолком `ct`. Участник часто шлёт по одному конверту.

### `OfflineMailboxStore { recipient, envelopes }`

1. Разобрать `recipient` как `PeerId`. Не разобрался — ничего не писать, ответ `OfflineMailboxDeliver` с пустым списком.
2. Оставить конверт, только если он v3 снаружи: `v = 3`, пустые `sender` и `kind`, нулевой `sender_pk`, `message_id` 1..128 символов, `eph` не нули, `ct` не пуст и не длиннее 64 КиБ. Остальное выкинуть, не открывая `ct`.
3. Лимит на Noise-`PeerId` загрузившего, окно 60 секунд: не больше 600 запросов `Store`, не больше 600 принятых конвертов, не больше 48 МиБ по сумме `|ct|`. Не влезло — не принимать ни одного конверта этого запроса.
4. В одном ящике от одного загрузившего уже лежит не больше 256 конвертов и 8 МиБ. Принять префикс списка, который умещается.
5. Новый ящик при уже занятых 4096 ящиках не создавать.
6. В ящике схлопнуть по внешнему `message_id`: такой id уже есть — пропустить.
7. После записи в ящике не больше 1024 конвертов и 32 МиБ. Лишнее снимается с головы (старые раньше).
8. Конверт живёт 7 суток с момента, когда диспетчер его принял. Время приёма на провод не пишется; его помнит диспетчер. Просроченное стирается и в `Deliver` не попадает.
9. Ответ `Ack`, если хотя бы политика шагов 3–5 не отказала и каждый оставшийся конверт либо записан, либо уже был (дубликат). Ответ `OfflineMailboxDeliver { envelopes: [] }`, если запрос был непустой, а принять нельзя (лимит, потолок ящиков, ни один конверт не v3). Пустой запрос — `Ack`.

`Ack` значит «диспетчер принял ответственность». Пустой `Deliver` на `Store` значит «не принял, отправитель оставляет письмо у себя и повторит». Это не выдача почты.

Диспетчер не смотрит внутрь `ct`, не проверяет подпись отправителя и не узнаёт `kind`. Квота «загрузившего» — это Noise-сторона `Store`, не внутренний отправитель: в v3 его на ящике нет.

### `MailboxChallengeRequest { recipient }` / `MailboxChallenge { nonce, ts }`

Участник сначала просит nonce. Диспетчер отвечает `MailboxChallenge`: 32 случайных байта и свой `ts` (unix-секунды). Nonce помнит, пока `ts` внутри ±2 минут, и принимает его один раз. Чужой `recipient` (не PeerId) — `Ack`, nonce не выдаёт.

### `OfflineMailboxQuery { recipient }`

Диспетчер этого дерева выдаёт ящик, когда `recipient` разбирается в тот же `PeerId`, что Noise этого соединения. Иначе `Ack`, ящик не трогать. Чужому ящику не подтверждают даже факт, что он непуст: ответ тот же, что у пустого своего. Поля `ts`, `nonce` и `sig` клиент не пишет, пока они нулевые: лишние поля этот диспетчер не разбирает.

1. Свой ящик: забрать пачку с головы. Первый конверт берётся всегда, даже если он один больше лимита. Следующий не берётся, если сумма объёмов (`|ct|+96`) превысит 512 КиБ.
2. Взятые конверты стираются из ящика до отправки ответа. Пустой слот удаляется. Остаток ждёт следующего `Query`. Повторно ту же пачку не отдают.
3. Пачка пустая — ответ `Ack`. Иначе `OfflineMailboxDeliver { envelopes }`.

Диспетчер не толкает почту сам. Первый `Query` клиент шлёт, как только TCP до диспетчера есть, и дальше примерно раз в секунду. После непустого `Deliver` остаток забирает следующий `Query`, не немедленно в том же залпе.

Схема кадра умеет ещё `MailboxChallengeRequest { recipient }`, `MailboxChallenge { nonce[32], ts }` и подпись. Сообщение подписи:

```
"VOID_MAILBOX_QUERY_v1" || recipient.to_bytes() || ts_le || nonce[32]
```

`protocol-conformance` проверяет эту подпись: nonce одноразовый, `ts` внутри ±2 минут, ключ — тот, чей `PeerId` равен `recipient`. Диспетчер этого дерева challenge не выдаёт и подпись не смотрит. Клиент на него эти кадры не шлёт. Через onion Noise-пир выхода — предыдущий hop, поэтому выдача по одному сравнению PeerId там не работает. Пока `Query` идёт по прямому TCP владельца, диспетчер сверяет этот TCP.

Выход луковицы на диспетчере печать не открывает: он пересылает `OnionDeliver` на `next` ([09-onion.md](09-onion.md)). Ящик пополняет прямой `OfflineMailboxStore`. `Ack` hop'у значит «ячейка принята», не «конверт записан».

### Очередь контакта

Кадры есть в схеме. Диспетчер этого дерева их не разбирает и ящик по-прежнему индексирует `recipient`. Клиент всё равно кладёт копию `OfflineMailboxStore`. Читает получатель сегодня её.

Когда диспетчер очередь обслуживает, правила такие. Владелец очереди — свежий Ed25519, не PeerId получателя. `queue_id` и `write_token` — по 32 случайных байта. Срок — 14 суток. `CreateQueue`:

```
queue_id[32], owner_pk, write_token[32], expiry, sig
```

`owner_pk` — protobuf этого Ed25519. Подпись покрывает

```
"VOID_QUEUE_CREATE_V1\0" || queue_id || write_token || expiry_le
```

`expiry > now`. Грант `(queue_id, write_token, expiry)` уходит отправителю внутри E2EE и только после Hello с битом `4`. `QueueStore`:

```
queue_id[32], proof[32], blob
```

`blob` — ровно 64 КиБ: `u32le` длины bincode-конверта, сам конверт, хвост нулями. Дольше бакета письмо в очередь не кладётся. `proof` — SHA-256 от

```
"VOID_QUEUE_WRITE_V1\0" || write_token || queue_id || blob
```

`QueueQuery` подписывает тот же ключ владельца:

```
"VOID_QUEUE_QUERY_V1\0" || queue_id || ts_le || nonce[32]
```

После 64 записей или когда до `expiry` меньше суток владелец заводит новую очередь. Старый `queue_id` выдаётся до своего `expiry`. В логе такого `Store` — короткий `queue_id` и размер бакета.

### Что участник делает с `Deliver`

Открывает текущим signed-prekey, предыдущим, оставшимися одноразовыми и X25519 из своего `PeerId`. Письмо с `VQK1` открывается ещё и секретом ML-KEM этого prekey. Письмо с `opk_id` открывается парой signed-prekey и этого одноразового, после чего одноразовый стирается. Чужая сторона, подмена `ct`, чужой `recipient` в AAD, v1 — выброс. Для `dm` и `group` сверяет `sender_id` с подписавшим.

## DHT-значение ящика

Ключ: байты `"/void/mailbox/"` || `recipient.to_bytes()`.

Значение — bincode 1.3 (little-endian, длины по 8 байт, без имён полей) непустого списка тех же объектов, что и JSON-конверт. Порядок полей: `v`, `sender`, `sender_pk`, `message_id`, `kind`, `eph`, `nonce`, `ct`. Весь блоб ≤ 64 КиБ, в списке ≤ 64 конвертов. Читатель может принять старый JSON-массив той же формы. Писатель новых записей шлёт bincode. Срок записи — 7 суток. Проверка «это v3» та же, что в шаге 2 `Store`. Иное значение узлы VOID не кладут ([06-discovery.md](06-discovery.md)).

DHT-значение prekey, ключ `"/void/prekey/"` || `owner.to_bytes()`:

v2:

```
pk[32] || 0x02 || not_after_le_u64
|| u16le(len(sig)) || sig || u16le(len(pubkey_pb)) || pubkey_pb
```

v3, ключ инкапсуляции сразу после срока:

```
pk[32] || 0x03 || not_after_le_u64 || kem_ek[1184]
|| u16le(len(sig)) || sig || u16le(len(pubkey_pb)) || pubkey_pb
```

Хвоста после `pubkey_pb` нет. Узел кладёт запись, только если подпись этой версии сошлась и срок годится для печати (`now < not_after ≤ now + 30 суток`). Метку `0x02` проверяют раньше `0x03`. v1 (нет метки) подпись может подтвердить, в хранилище её не кладут.

| Наблюдатель | Видит | Не видит |
|-------------|-------|----------|
| Диспетчер ящика | `recipient`, внешний `message_id`, `|ct|` (бакет дополнения), время приёма, `PeerId` загрузившего `Store` | отправителя, настоящий id, `kind`, тело, кому ещё ушли копии того же текста |
| Владелец на `Query` | пачку своих конвертов; после вскрытия — подписавшего и `kind` | конверты, которые диспетчер ещё не отдал (они стёрты только у него в этой пачке) |
| Чужой участник, сделавший `Query` | ответ `Ack` | есть ли ящик и что в нём |
| Узел DHT | ключ с `PeerId` получателя и непрозрачный блоб v3 | то же, что диспетчер не видит внутри `ct` |
| Загрузивший | `Ack` (принято) или пустой `Deliver` (отказ) | чужие конверты в этом ящике |
