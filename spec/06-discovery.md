# 06. Обнаружение

Поток Kademlia — `/void/kad/1.0.0`, режим сервера у диспетчера и у участника, который отвечает на запросы. Это указатель, не лента. Текст чата, кадр ratchet, файл, секрет сессии и ячейка onion в DHT не пишутся.

Чужой DHT (в том числе IPFS) этим именем не является. Узел VOID не обслуживает другой протокол Kademlia как свой.

## Какие значения можно положить

Общая проверка `dht_record_allowed` узнаёт три формы: prekey, одноразовый набор и ящик v3. Новый `put` при включённой очереди уже другой. Пишется только подписанный prekey. `/void/mailbox/` не пишется: это был бы второй ящик по PeerId. Запись, которая уже лежит, не стирается и доживает свой TTL. Ключа `/void/queue/` нет: id очереди в DHT снова показывал бы, куда смотреть. `/void/opk/` не пишется, и одноразовый ключ не добавляется в значение prekey.

| Ключ | Значение |
|------|----------|
| `"/void/prekey/"` \|\| `PeerId::to_bytes()` | подписанный prekey v2 (метка `0x02`) или v3 (метка `0x03` и ключ ML-KEM-768), срок ещё позволяет печать ([05-envelope.md](05-envelope.md)) |
| `"/void/opk/"` \|\| `PeerId::to_bytes()` | форма старой записи: `0x01` и 1..16 одноразовых ключей. Новый `put` отвергается |
| `"/void/mailbox/"` \|\| `PeerId::to_bytes()` | форма старой записи: bincode списка конвертов v3. Новый `put` отвергается |

Prekey v1 (нет метки `0x02` и нет метки `0x03`) подпись может подтвердить, но в хранилище он не кладётся: печатать им нельзя. Ящик v1 и v2 не кладётся. Пустой список одноразовых ключей не кладётся. Ключ, у которого хвост после префикса не является `PeerId`, не кладётся.

Кворум публикации, которым пользуется участник, — один ответ. Это не секретность, это «хватило одной копии».

## Чего в значениях нет

Даже под разрешённым префиксом значение не содержит:

- JSON чата и команд `delete` / `read` / `group_sync` в открытом виде;
- открытого `sender`, `kind`, настоящего `message_id` (в v3 их нет снаружи);
- байтов файла и WAV. Участник не кладёт в DHT конверт с `voice_chunk` или `file_chunk`: проверка ключа `kind` внутри `ct` не видит;
- статического секрета, корневого ключа, ключей цепи, пропущенных `MK`;
- секрета hop и открытого текста ячейки.

Узел, который видит `put` с другим ключом или с открытым текстом, запись не хранит. Ошибка хранилища наружу может выглядеть как отказ по размеру: отдельного кода «запрещённый ключ» протокол Kademlia здесь не добавляет. Для второй реализации важен отказ, не строка ошибки.

## Провайдер, не значение

Участник может объявить себя провайдером ключа, равного своим байтам `PeerId` (`start_providing`). Это не запись-значение: в нём нет тела сообщения, только «этот `PeerId` достижим у этого провайдера». Поиск адреса — `get_providers` и ближайшие узлы по тому же ключу.

Адрес в таблицу попадает после живого обмена, а не из произвольной строки в значении DHT. Слухи о диспетчерах между участниками идут `BootstrapGossip` по `/void/chat/1.0.0`, не записью DHT:

```
BootstrapGossip { addrs: [multiaddr, …], onion_keys: [hint, …] }
```

`addrs` — до 32 строк, каждая до 512 байт, после разбора — TCP multiaddr диспетчера с `/p2p/<PeerId>`. QUIC-адрес диспетчера участник в набор для набора не берёт. `onion_keys` — дескрипторы hop ([09-onion.md](09-onion.md)), не больше 32. У участника слух не заменяет Identify: ключ hop, который он уже видел в Identify, более низкая эпоха не перетирает, и адреса этого слуха он не пишет. Диспетчер — иначе: подписи v1 хватает, чтобы запомнить адрес. Пустой `sig2` оставляет `learned_epoch = 0`, адреса всё равно пишутся. Это каталог, не ящик.

| Наблюдатель | Видит | Не видит |
|-------------|-------|----------|
| Участник DHT | ключ prekey, непрозрачное значение, объявления провайдера, адреса узлов в таблице. Старый ящик может ещё лежать до TTL | текст, файл, ratchet, id очереди, одноразовый prekey |
| Диспетчер | то же, плюс кто сделал `put` (издатель записи, если стек его передал) | содержимое `ct` |
| Участник, читающий чужой ключ | отказ на новый `/void/mailbox/` и на `/void/opk/`. Читается подписанный prekey | ленту сообщений: её нет |
