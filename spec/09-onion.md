# 09. Onion

Onion закрывает не текст (текст уже в ratchet), а знание пары. Каждый hop снимает один слой. Один диспетчер на пути пару не прячет: снимать больше некому.

Цепочка из тех диспетчеров, у которых есть свежий ключ hop и которые есть в наборе известных диспетчеров:

| Сколько таких узлов | Сколько hop |
|---------------------|-------------|
| 0 | без onion: прямой кадр или circuit |
| 1 | 1 |
| 2 | 2 |
| 3 и больше | 3; вход — тот, с кем уже есть соединение |

Один и тот же узел не стоит и входом, и выходом. Второй и третий hop предпочитают другой IPv4 `/16`, другой IPv6 `/32` и другую непустую метку оператора. Это выбор отправителя, не байт, который hop обязан проверить.

v2 — если у **каждого** hop на выбранном пути есть свежий дескриптор. Иначе весь путь заворачивается в v1. Смешивать версии слоёв в одной ячейке нельзя.

Живой `Encrypted` крупнее бакета v2 в ячейку не кладут: файл и длинный чанк идут прямым каналом или ящиком.

## Дескриптор

Hop — диспетчер. В Identify `agentVersion` поля через `;`:

```
void-bootstrap-node/<версия>
;onion=<64 hex X25519>
;osig=<hex подписи v1>
;epoch=<u64 десятичный>
;until=<unix>
;op=<метка>
;osig2=<hex подписи v2>
```

Порядок полей может быть любым: разбор по имени ключа до следующего `;`.

Подпись v1 (ключ hop навсегда связан с `PeerId`, без срока):

```
"VOID_ONION_PK_BIND_V1\0" || peer.to_bytes() || pk[32]
```

Подпись v2:

```
"VOID_ONION_DESC_V2\0"
|| u16le(len(peer.to_bytes())) || peer.to_bytes()
|| pk[32]
|| epoch_le || not_after_le
|| u16le(len(op)) || op
```

`op` — до 32 байт, без байтов `< 0x20` и без `;`. Подписи делает транспортный ключ этого `PeerId`.

Дескриптор v2 свежий, если `epoch > 0`, `not_after > now` и `not_after ≤ now + 30 суток`. Больший `epoch` с верной подписью заменяет уже известный ключ. Hop меняет X25519 раз в 7 суток и ещё сутки открывает ячейки предыдущим секретом, потом стирает его. На проводе в один момент объявлен один `pk`.

Только `;onion=` без `osig` — старый hop. Участник, который видел его в Identify, может поставить его в путь v1: Noise уже связал `PeerId`. В gossip такой ключ не пересылается. Если `osig` есть и не сходится, ключ не берётся. Путь v2 требует у каждого hop и v1-подпись, и свежий дескриптор v2.

Тот же дескриптор едет в `BootstrapGossip.onion_keys`: `peer_id`, `pk_hex`, `addrs[]`, `sig_hex`, `epoch`, `not_after`, `operator`, `sig2_hex`. Слух без подписи v1 игнорируется. Слух не затирает ключ, уже виденный в Identify, если `epoch` не выше.

## v1

Полезная нагрузка слоя — JSON:

```
{ "next": "<PeerId base58>", "inner": <JSON значение> }
```

Ключ:

```
HKDF-SHA256("VOID_ONION_SALT_v1", DH(eph, hop_pk), "VOID_ONION_v1", 32)
```

Общий секрет из нулей (точка малого порядка) отвергается. AEAD с пустым AAD, nonce 12 случайных байт. `ct` не пуст и не длиннее 256 КиБ.

На провод к первому hop:

```
Onion { eph[32], nonce[12], ct }
```

Внутри `ct` после вскрытия — снова `Onion` (следующий слой) либо самый внутренний кадр:

```
OnionDrop { src: "<PeerId отправителя>", packet: Hello | Encrypted | Ack }
```

Слои заворачиваются от получателя к входу: `next` последнего слоя — получатель, `next` внешнего — первый hop.

Hop v1:

1. Открыть своим секретом. Не открылось — ответить `Ack` и забыть.
2. `next` обязан разбираться как `PeerId`.
3. Вперёд слать только после Identify с `next` (или набора к нему). Не слать себе.
4. Ответить отправителю ячейки `Ack` сразу: ячейка не ждёт конца пути.
5. Не писать `next` и `src` в журнал.

Получатель принимает `OnionDrop` только от диспетчера, у которого сам видел `;onion=` в Identify, и только если внутри `Hello`, `Encrypted` или `Ack`. `src` не равен получателю и не равен hop. В v1 выходной hop и получатель видят `src`.

## v2

Ячейка фиксированной длины: 2048, 16384 или 65536 байт. Заголовок — всегда 3 слота, поэтому длина не говорит, какой это hop по счёту.

Слот — 124 байта: `eph[32] || nonce[12] || ct[80]`. Три слота — 372 байта, дальше тело.

Открытый текст слота — 64 байта (AEAD даёт 80):

| Смещение | Смысл |
|----------|--------|
| 0 | версия `2` |
| 1 | `1` — этот hop выход (доставить), `0` — переслать ячейку |
| 2 | длина `PeerId` `next`, 1..48 |
| 3 .. | байты `next` |
| хвост | случайные |

Ключи слота, `hop_pk` — объявленные 32 байта этого hop:

```
HKDF-SHA256("VOID_ONION_SALT_v2", DH(eph, hop_pk),
            "VOID_ONION_v2" || eph || hop_pk || which, 32)
```

`which` — `HDR` для AEAD слота и `STREAM` для тела. AAD у слота пустой.

Тело после заголовка: первые 4 байта — `u32le` длины печати, затем печать, остаток до конца бакета — случайные байты. Каждый hop XOR-ит всё тело (включая длину и мусор) потоком:

```
блок = HKDF-SHA256(stream_key, counter_le_u32, "VOID_ONION_v2_STREAM", 32)
counter = 0, 1, 2, … пока тело не кончится
```

Отправитель XOR-ит тело ключами от последнего hop к первому и кладёт слот `i` для hop `i`. Пустые слоты (если hop меньше трёх) — случайные байты.

На провод:

```
Onion2 { cell_b64 }
```

`cell_b64` — стандартный Base64 с `=`.

Hop v2, слот 0:

1. Длина ячейки — ровно один из трёх бакетов. Иначе молча `Ack`.
2. Открыть слот. Байт 0 обязан быть `2`.
3. XOR тела своим `STREAM`.
4. Если байт 1 равен 0: сдвинуть слоты 1 и 2 в начало, на место третьего записать 124 случайных байта, длина ячейки та же. Переслать `Onion2` на `next`.
5. Если байт 1 равен 1: это выход. `next` — получатель. Переслать ему не ячейку, а

```
OnionDeliver { body_b64 }
```

`body_b64` — Base64 **тела после XOR** (с `u32le` длины и хвостом бакета), не вся ячейка и не внутренняя печать отдельно.

6. Лимит пересылки: не больше 600 ячеек в минуту от одного предыдущего hop и не больше 6000 в минуту со всех. Сверх лимита ячейка не уходит. В журнал не попадают `next` и отправитель (в v2 отправителя на hop нет).
7. Входному отправителю ячейки — `Ack`, как в v1.
8. Повтор. Ключ — BLAKE2b-128(`eph` слота 0 || `ct` слота 0), без nonce между ними. Hop помнит ключ 14 суток, не дольше срока своего дескриптора. Тот же ключ снова — ячейку не снимает и не пересылает. `Ack` отправителю слота всё равно уходит: это «ячейка получена», не «её передали дальше».

Получатель `OnionDeliver`:

1. Только от диспетчера, чей onion-ключ получатель видел в Identify.
2. `deliver = body[4 .. 4+u32le(body[0..4])]`. Это печать.
3. Печать: `eph[32] || nonce[12] || ct`.
4. Ключ — X25519 из своего `PeerId`, не prekey:

```
HKDF-SHA256("VOID_ONION_SALT_v2", DH(eph, identity_pk),
            "VOID_ONION_SEALED_v2" || eph || identity_pk, 32)
```

5. Открытый текст печати: `u32le(len) || mail`. `mail`:

| Байт 0 | Дальше |
|--------|--------|
| `1` | `u8` длина `PeerId` отправителя, байты `PeerId`, JSON `Hello` |
| `3` | `u8` длина, байты `PeerId`, больше ничего — это `Ack` |
| `2` | `dh_pub[32] || pn_le || n_le || ciphertext` ratchet, без `PeerId` |
| `4` | `u32le` длины JSON, JSON кадра ящика, token[16], адрес ответа и hop'ы обратно. Отправителя в кадре нет |

`Hello` и `Ack` несут отправителя внутри печати. `Encrypted` получатель пробует открыть на живых сессиях: сошёлся ratchet — этот сосед и есть отправитель. Выходной hop печати не открывает. Он видит длину печати (она в начале тела) и `PeerId` получателя. `PeerId` отправителя в ячейке v2 нет.

Байт `4` — кадр ящика (`OfflineMailboxStore`, `OfflineMailboxQuery`, `MailboxChallengeRequest`, `MailboxChallenge`, `OfflineMailboxDeliver` или `Ack`). В JSON нет отправителя. Exit, если `next` — он сам, открывает печать и кладёт `Store` по `recipient` из кадра (после этапа E — по queue id). Подпись `Query` та же, что на прямом TCP. Обратный путь (token, кому вернуть, hop'ы) лежит в той же печати, не на ячейке. Ответ — новая ячейка по этому пути. `Ack` входного hop — только «ячейку принял», это не сдача конверта. Один `Store` — один конверт, и он должен влезть в бакет 2/16/64 КиБ. В v1 такой кадр не заворачивают: последний слой v1 несёт `src`.

Ответ получателя — новая ячейка к тому соседу, которого он узнал, а не «назад по тому же пути» как состояние hop: hop пути не помнит.

| Наблюдатель | Видит | Не видит |
|-------------|-------|----------|
| Вход v2 | IP и `PeerId` отправителя ячейки, `next`, бакет 2/16/64 КиБ | получателя, `Hello`, текст |
| Середина v2 | два соседних `PeerId`, тот же бакет | оба края и смысл |
| Выход v2 | `PeerId` получателя, бакет, длину печати | `PeerId` отправителя, `Hello`, заголовок ratchet, текст |
| Выход v1 | `next`, а на последнем слое ещё `OnionDrop.src` и тип кадра | открытый текст ratchet |
| Получатель v2 | после печати — отправителя `Hello`/`Ack` или сессию, чей ratchet сошёлся | какой был входной IP |
| Наблюдатель всей цепочки | связь бакетов по времени | текст; v2 не выравнивает ячейки между разными бакетами и не мешает пачки |
