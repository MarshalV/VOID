# 03. Сессия

После `Hello` полезная нагрузка — вариант `Encrypted` на `/void/chat/1.0.0`:

```
Encrypted { header: { dh_pub[32], pn: u32, n: u32 }, ciphertext: bytes }
```

`ciphertext` — ChaCha20-Poly1305. Открытый текст — один кадр: JSON чата, команда или кадр вложения ([04-attachments.md](04-attachments.md)). Промежуточный узел эти байты не читает: они лежат внутри Noise, а на onion ещё и внутри ячейки.

Это Double Ratchet VOID, не копия Signal байт в байт. Ниже — точные KDF, иначе вторая реализация не откроет кадр.

## Корни

`HKDF-SHA256(salt, ikm, info, L)` — как в [каталоге](README.md).

Начальный корневой ключ, одинаковый у обеих сторон:

```
RK0 = HKDF-SHA256("VOID_SALT", DH(static_a, static_b), "VOID_INIT_RK", 32)
```

Шаг корня:

```
out = HKDF-SHA256(RK, DH_shared, "dr_ratchet", 64)
RK' = out[0..32]
CK  = out[32..64]
```

Шаг цепи. `CK.index` начинается с 0, на проводе не передаётся:

```
MK = HKDF-SHA256(CK.key, "message_key", index_be_u32, 32)
CK.key = HKDF-SHA256(CK.key, "chain_key", index_be_u32, 32)
CK.index += 1
```

`index` в `info` — 4 байта big-endian **до** увеличения. `MK` — ключ одного кадра.

Nonce AEAD — 12 байт: первые 4 — `n` little-endian, остальные нули. `n` в заголовке — это номер в текущей цепи отправки, тот же, что попал в nonce.

## Кто кем становится после Hello

Пусть инициатор A прислал эфемер `eA` и статический `sA`, ответчик B — `eB` и `sB`.

Ответчик B:

1. `DH(sB, eA)` → цепь приёма.
2. `DH(eB, eA)` → цепь отправки. Его `dh_pub` пока равен `eB`.

Инициатор A делает на один шаг больше, ещё до первого кадра:

1. `DH(eA, sB)` → цепь отправки (её сразу заменяют).
2. `dhr = eB`, `DH(eA, eB)` → цепь приёма.
3. Новый случайный `dhs`. `DH(dhs, eB)` → цепь отправки. Первый кадр A несёт **этот** `dh_pub`, не `eA`.

Поэтому первый кадр A не совпадает с `dhr` у B (`eA`). B выполняет DH-шаг (ниже) и только тогда получает цепь, парную шагу 3. Цепь `DH(sB, eA)` на проводе не используется.

Если B успевает сказать первым, его `dh_pub` равен `eB`, а у A цепь приёма уже от `DH(eA, eB)`. Шага DH нет, кадр открывается. Следующий кадр A уже с новым `dh_pub`.

## DH-шаг

Когда `header.dh_pub` не равен текущему `dhr`:

1. Запомнить пропущенные ключи старой цепи приёма до `header.pn` (не включая `pn`).
2. `pn_local = ns`, `ns = 0`, `nr = 0`.
3. `dhr = header.dh_pub`.
4. `DH(свой dhs, dhr)` → новая цепь приёма.
5. Новый случайный `dhs`. `DH(новый dhs, dhr)` → новая цепь отправки.

Затем пропуск до `header.n` и один шаг цепи приёма — это `MK` кадра.

Каждый ход реплики меняет DH-ключ. Повторно слать с тем же `dhs` после чужого нового `dh_pub` нельзя: шаг выше уже заменил его.

## AAD

Каждый кадр сессии шифруется с AAD:

```
"VOID_RATCHET_HDR_V1" || dh_pub || pn_le || n_le || peer_aad
```

Префикс — 19 байт ASCII, без нуля на конце.

`peer_aad` — два `PeerId::to_bytes()` в лексикографическом порядке байтов: меньший, затем больший. Обе стороны вызывают это от одной и той же пары, порядок аргументов у вызова не важен.

Сессия, открытая принятым Hello, шлёт и принимает только кадры с этим AAD. Требование включено сразу, до первого кадра. Кадр с пустым AAD отвергается.

Приём — одна попытка, с AAD. Подмена `dh_pub`, `pn` или `n` ломает тег.

## Пропущенные ключи

Состояние меняется только после успешного AEAD. Приёмник считает кадр на копии сессии и подменяет живую сессию лишь при успехе. Поддельный кадр не двигает счётчики и не заполняет склад.

Склад: пара `(dh_pub, n)` → `MK`.

- за один заголовок нельзя перешагнуть больше 1000 индексов;
- в складе не больше 4096 ключей;
- ключ старше 1 часа стирается;
- удачный разбор стирает использованный `MK`;
- повтор того же заголовка после успеха — отказ.

Превышение прыжка или потолка — отказ всего кадра, склад не растёт.

## Открытый текст кадра

Не длиннее 64 КиБ. Либо JSON-объект (первый байт `{`), либо кадр `VfC1` / `VfP1`.

JSON сообщения чата, поля:

| Поле | Предел |
|------|--------|
| `id` | 1..64 байт, или пусто |
| `sender_id` | ≤ 512 |
| `sender_name` | ≤ 256 |
| `text` | ≤ 16 КиБ |
| `timestamp` | ≤ 64 |
| `recipient_id` | ≤ 512, необязательно |
| `group_id` | 32 hex, необязательно |
| `voice` | `{transfer_id: 32 hex, duration_secs}` — 0 < длительность ≤ 3600 |
| `file` | `{transfer_id: 32 hex, filename, size}` — имя 1..256, без `/` и `\`, `size` ≤ 512 МиБ |
| `delivery` | `pending` / `delivered` / `read` — подсказка, не доказательство |

Пустые `text`, `voice` и `file` одновременно — не сообщение. `file.local_path`, если пришёл, получатель отбрасывает.

Команды (тоже JSON, поле `kind`):

| `kind` | Поля | Предел |
|--------|------|--------|
| `delete` | `message_ids[]` | 1..256 id, каждый 1..64 байт |
| `delete_ack` | `deleted[]`, `missing[]` | сумма ≤ 256 |
| `read` | `message_ids[]` | как `delete` |
| `delivered` | `message_ids[]` | как `delete` |
| `voice_ack` | `transfer_id` (32 hex), `ok` (bool) | получатель шлёт `ok: true` только после совпадения хэша файла |

`delivered` и `read` — отдельные кадры, не поле `delivery` в сообщении. Групповые команды — [10-groups.md](10-groups.md).

| Наблюдатель | Видит | Не видит |
|-------------|-------|----------|
| Транспорт между двумя участниками | размер `ciphertext`, время, оба `PeerId` Noise | `header` в открытом виде только внутри Noise; текст — нет |
| Диспетчер circuit | размер потока | `dh_pub`, `n`, текст |
| Hop v1, последний слой | JSON `Encrypted`: `dh_pub`, `pn`, `n`, размер `ciphertext` | открытый текст и `MK` |
| Hop v2 | бакет | заголовок ratchet и текст |
| Получатель | текст и то, что заголовок не подменён | будущие `MK`; старые `MK` стёрты; кадра без AAD у текущей сессии нет |
