# Ревизия безопасности VOID (p2p-messenger)

**Дата составления:** 2026-05-09  
**Охват:** исходники `src/` (без полного аудита `Cargo.lock`/CVE по зависимостям и всего стека libp2p).  
**Цель:** инвентаризация уязвимых и рискованных точек проекта.

---

## 1. Критичные / высокие риски

| # | Область | Файлы / узел | Суть |
|---|---------|--------------|------|
| 1 | Протокол чата: Plain | `main.rs`, `V1Packet` | **Исправлено:** вариант `Plain` удалён; принимается только зашифрованный чат (`Encrypted`) + служебные `Hello`/`Ack`. |
| 2 | Привязка E2EE к транспортной личности | `main.rs` (Hello), `crypto.rs` | **Исправлено:** в `Hello` добавлена подпись Ed25519 (libp2p `Keypair`) над привязкой `PeerId` отправителя/получателя и X25519-ключей; без валидной подписи хендшейк отвергается. |
| 3 | Парсинг после E2EE | `main.rs`, `serde_json` | **Исправлено:** после дешифрования — лимит размера JSON и длины полей `ChatMessage` (`parse_decrypted_chat_json`). |
| 4 | Bootstrap HTTP(S) | `main.rs`, `fetch_void_bootstrap_list`, `reqwest` | **Исправлено:** лимит размера тела ответа; опциональный allowlist хостов `VOID_BOOTSTRAP_TRUSTED_HOSTS`. **Certificate pinning** по-прежнему не внедрён (см. п. 5 ниже при необходимости). |

## 2. Средние риски

| # | Область | Файлы / узел | Суть |
|---|---------|--------------|------|
| 5 | Double Ratchet | `crypto.rs`, `SecureSession` | Упрощённая модель DR, свой HKDF (salt/info). Лимит **100** `skipped_keys` с жёстким ошибочным завершением. Важны **availability** при джиттере/потере пакетов; нужен **внешний криптообзор** под целевую модель угроз. |
| 6 | Dial без PeerId | `main.rs`, `parse_seed_input` | Ввод `IP` / `IP:PORT` без `/p2p/<PeerId>`: повышенное доверие к конечному хосту **до** полной транспортной аутентификации через Identify/Noise по сценарию. |
| 7 | Vault: JSON после AES | `main.rs`, `Storage::load` | `serde_json::from_slice` без явного **версионирования** plaintext и без **верхней границы** размера JSON — поверхность для ресурсного давления при обработке `vault.bin`. |
| 8 | Секреты в RAM | `main.rs`, UI unlock | Мастер vault частично в `Zeroizing`; пароли в **`String`**. Нет режима «заблокировать» с очисткой сессии из RAM. Стандартные угрозы: кейлоггер, дамп процесса. |
| 9 | Файлы: метаданные оффера | `file_transfer.rs`, `/void/file/1.0.0` | Имя, размер, хэш в оффере — не на уровне E2EE-содержимого чанков; **метаданные** более доступны наблюдателю транспорта/relay. |
| 10 | Паники на старте сети | `main.rs`, `SwarmBuilder`, `listen_on` | Множественные `.unwrap()` — аварийный выход процесса вместо управляемой деградации (**availability**). |
| 11 | Отправка чата | `main.rs`, `SendMessage` | `serde_json::to_vec(&msg).unwrap()` — теоретическая паника вместо `Result`. |

## 4. Что уже сделано хорошо (кратко)

- Транспорт **Noise** + отдельный **E2EE** слой (ChaCha20-Poly1305 и кастомный ratchet после статического обмена в Hello).
- **Vault**: AES-256-GCM; мастер в **`void.key`** с обёрткой **Argon2id + AES-GCM** и экран пароля на старте.
- Явная **зероизация** чувствительных полей и `skipped_keys` в `SecureSession` при `Drop`.
- **Чанки файлов** после установления DR шифруются тем же сеансом — содержимое лучше защищено от оператора relay, чем сырой транспортный поток.
