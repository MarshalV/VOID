# VOID — анализ безопасности и план устранения

Дата: 2026-10-04. Объект: репозиторий `p2p-messenger` (клиент + протокол `/void/…`).
Сторона hop'а onion (unwrap и forward на ноде) живёт в `MarshalV/bootstrap_node` и здесь не проверялась — к ней ниже даны требования.

Документ лежит в `documents/` (в `.gitignore`). Не публиковать до исправления пунктов уровня «критично» и «высоко».

---

## 1. Что это и как устроено

VOID — протокол доставки сообщений поверх libp2p и десктоп-клиент на нём.

| Слой | Что делает | Где в коде |
|---|---|---|
| Транспорт | TCP + Noise + Yamux, Identify `/void/v1`, Kademlia `/void/kad/1.0.0`, mDNS, Circuit Relay v2 | `network.rs::build_void_swarm` |
| Диспетчер (bootstrap) | discovery, relay Hop, офлайн-ящик, каталог prekey, onion-hop | отдельный репозиторий |
| Кадры | `V1Packet` по `/void/chat/1.0.0` (JSON request-response) | `protocol.rs:600` |
| E2EE | `Hello` (X25519 static + ephemeral, подпись Ed25519 к PeerId) → Double Ratchet, ChaCha20-Poly1305 | `crypto.rs`, `protocol.rs::build_v1_hello` |
| Офлайн | ECIES-конверт к prekey получателя, хранение на bootstrap/пире/DHT | `offline_mail.rs`, `relay_mailbox.rs` |
| Onion | `VOID_ONION_v1`: до 3 слоёв X25519+HKDF+ChaCha20-Poly1305 к ключам нод | `onion.rs`, `network.rs` |

Модель угроз по README: узел-диспетчер не должен читать текст; onion должен скрывать от входа получателя, а от выхода — IP отправителя. Защиты от глобального наблюдателя нет, и README это прямо пишет.

## 2. Логика onion-подключения — как она работает сейчас

### 2.1 Откуда берутся ключи hop'ов

1. **Identify** подключённой ноды: `agent_version = "void-bootstrap-node/…;onion=<64hex>"` → `onion_keys.insert(peer, pk)` (`network.rs:7730`). Ключ получен по Noise-соединению с этим PeerId, но сам ключ ничем не подписан.
2. **BootstrapGossip.onion_keys** (`OnionHopHint { peer_id, pk_hex, addrs }`) от **любого подключённого VOID-клиента** → `ingest_onion_hints` (`network.rs:416-455`):
   - `onion_keys.insert(pid, pk)` — **перезаписывает** уже известный ключ;
   - `bootstrap_peer_ids.insert(pid)` — пир объявляется «bootstrap»;
   - `addrs` уходят в `merge_bootstraps_into_swarm` и затем в набор (`dial_missing_bootstraps`).
3. Каталог раздаётся дальше (`collect_onion_hints`, до 32 записей) — эпидемически всем подключённым не-bootstrap пирам.

### 2.2 Выбор пути (`onion.rs:118-155`)

```
pool  = keys ∩ bootstrap_ids
entry = случайный из pool ∩ connected
want  = 1 | 2 | 3 по размеру pool
rest  = shuffle(pool \ entry)[..want-1]
```

Путь выбирается **заново для каждого пакета**. Проверок разнообразия операторов, подсетей или AS нет. Guard-узла нет. Middle и exit могут быть узлами, о которых клиент знает только по gossip.

### 2.3 Отправка (`network.rs:2447-2500`, `protocol.rs:670-686`)

```
send_v1_to_peer(dest, packet):
  если dest — bootstrap         → напрямую
  если hops пуст                → напрямую
  если dest уже подключён       → напрямую
  onion = wrap(hops, OnionDrop{src: local, packet})
  если wrap не удался           → НАПРЯМУЮ (молча)
  иначе send_request(hops[0], onion)
```

Слой (`onion.rs:158-184`): изнутри наружу — `OnionPayload{next, inner}` → JSON → seal к ключу hop'а → `{"Onion":{eph,nonce,ct}}` как `serde_json::Value` (где `ct` — **массив чисел**) → следующий слой.

### 2.4 Приём у получателя (`network.rs:5433-5463`)

- `V1Packet::Onion` клиенту → просто `Ack` (клиенты не hop'ы).
- `V1Packet::OnionDrop{src, packet}` **от любого пира** → `peer = src`, `request = *packet`, `onion_reply = Some(src)`. Дальше пакет обрабатывается **как пришедший от `src`** всеми обработчиками: `BootstrapGossip`, `OfflineMailbox*`, `Prekey*`, `DialBack`, `Hello`, `Encrypted`.
- Ответ (`rr_reply`, `network.rs:2502-2523`): `Ack` для onion не отправляется вообще, остальное уходит новым onion к `src`.

### 2.5 Что реально видит каждый участник (3 hop'а)

| Участник | Видит |
|---|---|
| Entry | IP Алисы, PeerId Алисы (Noise), следующий hop, размер ячейки |
| Middle | entry, exit, размер |
| Exit | **PeerId Алисы (`src` открытым текстом)**, PeerId Боба, тип внутреннего пакета (`Hello`/`Encrypted`), заголовок ratchet, размер |
| Боб | Алиса (по замыслу) |

Получается, что пару «Алиса ↔ Боб» exit знает всегда. Скрыт только IP Алисы. При 1 hop'е одна нода видит всё сразу.

## 3. Найденные недостатки

Уровни: **К** — критично, **В** — высоко, **С** — средне, **Н** — низко.

### К-1. `OnionDrop` принимается от кого угодно, `src` не проверяется — подмена отправителя

`network.rs:5441-5462`. Нет проверки, что отправитель `OnionDrop` — известная onion-нода. Нет проверки, что `src` действительно автор пакета. Нет ограничения типов внутреннего пакета.

Что это позволяет любому подключённому пиру (или любой exit-ноде):

- от имени любого контакта прислать `BootstrapGossip` — подмешать ноды и onion-ключи (см. В-2);
- от имени любого контакта прислать `DialBack` — заставить жертву набирать адрес, который выбрал атакующий (см. С-6);
- прислать `Encrypted` с поддельным заголовком от имени Алисы — сломать ratchet-сессию Боба с Алисой (см. В-5);
- повторить перехваченный `Hello` Алисы — сбросить сессию (см. С-1);
- через `onion_reply` направлять ответы жертвы на произвольный `src` (отражение и усиление).

### К-2. Офлайн-конверты не аутентифицированы — поддельные сообщения «от любого»

`offline_mail.rs:130-212`, `bridge.rs:1058-1148`.

`seal_for_recipient` — анонимный sealed box: ключ шифрования зависит только от `eph` и ключа получателя. Поля `sender` и `sender_pk` лежат открыто и в расшифровку не входят. Получатель берёт `msg.sender_id` из расшифрованного JSON и кладёт сообщение в чат этого отправителя.

Любой, кто знает prekey жертвы (а его раздаёт bootstrap по `PrekeyGet` и DHT), может положить в её ящик «сообщение от» любого контакта. Тип `group_sync` с `env.sender` тоже подделывается: так можно добавить жертву в группу или переписать состав, имя и создателя существующей группы.

Заодно нода видит метаданные `sender`, `recipient`, `kind`, `message_id` — это известно и описано, но в сочетании с подделкой хуже.

### К-3. Отравление prekey — потеря конфиденциальности офлайн-почты

`network.rs:6427-6436`, `bridge.rs:2211-2214`.

Ответ `PrekeyOffer`, для которого нет нашего исходящего `PrekeyGet` (ветка `else`), всё равно вызывает `remember_peer_prekey(pid, key)` для **произвольного** `peer_id`. Результат записывается в vault (`persist_vault`). Ответить таким пакетом может любой пир, которому мы отправили любой запрос: контакт, bootstrap или «bootstrap», подмешанный через gossip.

Кроме того, prekey на bootstrap и в DHT (`/void/prekey/<peer>`) не подписан identity-ключом владельца. Значение записи Kademlia берётся без проверки (`network.rs:8039-8056`). Злонамеренная нода или участник DHT подменяет prekey, и следующие офлайн-сообщения запечатываются к ключу атакующего.

Итог: атакующий, у которого лежит ящик (он сам bootstrap или подмешан как bootstrap), читает офлайн-почту.

### В-1. Exit-hop видит отправителя — onion не разрывает пару

`protocol.rs:660-686`. `OnionDrop.src` открытым текстом внутри последнего слоя. К этому добавляется:

- путь выбирается заново для каждого пакета (`select_hops` в `send_v1_to_peer`). За время переписки через роль exit проходят многие ноды пула, и **каждая** узнаёт пару;
- внутри часто лежит `Hello`, в котором есть static X25519 и подпись, привязанная к обоим PeerId. Это ещё одна прямая идентификация.

README обещает: «exit не видит IP Алисы». Формально это так, но PeerId — постоянный идентификатор, и он раскрыт.

### В-2. Gossip onion-ключей и bootstrap без подписи — Sybil и перехват пути

`network.rs:355-391`, `416-455`, `5466-5546`.

- Любой контакт рассылает `OnionHopHint` с подконтрольными PeerId и ключами. Те попадают в `bootstrap_peer_ids` и в пул hop'ов. При 10 поддельных записях против 2 настоящих middle и exit почти всегда достаются атакующему. Вместе с В-1 он узнаёт все пары.
- `onion_keys.insert` **перезаписывает** ключ настоящей ноды. Ячейка к ней не расшифруется (DoS onion), либо ключ уже подменён и связан с адресом атакующего.
- `merge_bootstraps_into_swarm` при совпадении `ip:port` **заменяет** multiaddr, а значит и PeerId настоящей ноды на присланный (`network.rs:368-376`). Подключение к настоящей ноде перестаёт проходить Noise — получается eclipse и DoS.
- Подмешанные «bootstrap» уходят в UI и сохраняются (`BootstrapsLearned` → `merge_learned_bootstraps`). Клиент начинает считать их диспетчерами: отправлять им офлайн-почту, prekey и запросы ящика (связь с К-3).

### В-3. Тихий откат с onion на прямую отправку

`network.rs:2474-2499`.

- `wrap_onion_packet` вернул `None` (ячейка > 3 MiB после раздувания JSON, см. С-2) → пакет уходит **напрямую** к `dest`. Пользователь об этом не узнаёт.
- Если `dest` уже подключён (LAN, circuit, DCUtR), onion не используется вовсе.
- Нет режима «только onion». Нет статуса «это сообщение ушло без onion». Есть только запись в trace.

Один и тот же разговор идёт то через onion, то напрямую. Корреляция тривиальна.

### В-4. Ложная доставка через onion — потеря сообщений

`network.rs:6340-6354`, `2508-2511`.

`Ack` на исходящий запрос считается подтверждением от адресата (`MessageDelivered`). При onion запрос уходит **entry-hop'у**, и подтверждение приходит от него. `Ack` Боба для onion-пакета намеренно выбрасывается. Сообщение помечается «доставлено» и снимается с повторов, даже если exit не дозвонился до Боба. Для файловых чанков (`outbound_chunk_requests`) — то же самое.

Точная семантика `Ack` на ноде — в репозитории bootstrap_node, но клиент в любом случае не отличает «hop принял» от «Боб получил».

### В-5. Double Ratchet меняет состояние до проверки AEAD; заголовок не аутентифицирован

`crypto.rs:225-249`, `200-223`.

`decrypt_payload` выполняет `skip_message_keys` и `dh_ratchet` **до** расшифровки. При ошибке AEAD состояние не откатывается. Заголовок (`dh_pub`, `pn`, `n`) не передаётся как associated data.

Атака: пакет `Encrypted{header{dh_pub: случайный}, ct: мусор}` от имени Алисы (через К-1 или любым пиром с её PeerId в роли `peer`) → у Боба выполняется DH-ratchet на мусорный ключ, и сессия с Алисой сломана. Код при этом пишет «сессию не сбрасываю» (`network.rs:6128-6130`), так что сессия остаётся сломанной до нового `Hello`. Вариант с `n = 4095` забивает буфер пропущенных ключей.

### С-1. Повтор `Hello` — сброс сессии

`network.rs:5740-5800`. В подписи `Hello` нет ни времени, ни счётчика, ни nonce. Входящий `Hello` при существующей сессии всегда её сбрасывает. Exit-hop видит `Hello` внутри `OnionDrop` и может повторять его когда угодно. В-5 и С-1 вместе дают постоянный DoS разговора.

### С-2. Размер ячейки выдаёт позицию hop'а и размер сообщения; раздувание JSON

`onion.rs:158-184`, `protocol.rs:670-686`.

- `Vec<u8>` в `serde_json` — массив чисел, примерно в 3,5 раза больше. Каждый слой кодирует предыдущий шифртекст снова, так что 3 слоя дают раздувание порядка ×40. Hop по размеру понимает, на какой он позиции, и коррелирует вход с выходом.
- Нет выравнивания (padding) и фиксированных размеров ячеек.
- `MAX_CT_BYTES = 3 MiB` на ячейку — дорогой разбор JSON на hop'ах и выход за лимит RR. Отсюда же откат из В-3.

### С-3. Статические onion-ключи без ротации, без защиты от повтора

`onion.rs:67-105`.

- Ключ hop'а живёт столько же, сколько нода. Утечка секрета расшифровывает все записанные ячейки за всё время: прямой секретности нет.
- Защиты от повтора на hop'е в протоколе нет: нет кэша `eph`, нет эпохи. Повтор ячейки — классическая атака подтверждения трафика.
- HKDF `info` не связывает `eph_pk` и `hop_pk`. Нет отказа на low-order точках (нулевой общий секрет). Риск невысокий, но это стандартная гигиена.

### С-4. Выбор пути слабый

`onion.rs:118-155`.

- Нет разнообразия: все три hop'а могут принадлежать одному оператору или подсети.
- Entry — подключённая нода. Обычно это та же нода, что даёт relay Hop и хранит офлайн-ящик. Она и так знает IP Алисы и метаданные ящика.
- Новый путь на каждый пакет (против В-1 нужен обратный подход: фиксированный guard и устойчивая цепочка на время сессии).
- При пуле из 2 у exit `src` и `dest`, а entry знает IP — вдвоём они раскрывают всё. Интерфейс показывает «onion» без предупреждения, что анонимности нет.

### С-5. Локальный relay-ящик: забор чужой почты и переполнение диска

`network.rs:5547-5586`, `relay_mailbox.rs:73-130`.

- `OfflineMailboxQuery{recipient}` выполняется без проверки, что `peer == recipient`. Любой может выгрести (`take_batch` удаляет) чужие конверты. Сообщения теряются, хотя прочитать их атакующий не может.
- `OfflineMailboxStore` — до 32 MiB и 1024 конвертов **на каждого** получателя, а число получателей не ограничено. Так можно заполнить диск. Флуд к одному получателю вытесняет его настоящие конверты (старые удаляются первыми).
- Те же проверки нужны на bootstrap_node.

### С-6. `DialBack` от кого угодно — раскрытие IP и засорение целей

`network.rs:5607-5659`. Любой пир (или поддельный `src` через К-1) присылает circuit-адреса через relay атакующего. Жертва набирает их (`PeerCondition::Always`) и раскрывает свой IP этому relay. Адреса ещё и сохраняются в `reconnect_targets`.

### С-7. Состояние группы без авторизации

`bridge.rs:1542-1615`. `merge_incoming_group_sync` целиком перезаписывает группу (имя, создатель, участники) по `group_id` от любого отправителя, если жертва есть в списке. Ни версии, ни подписи создателя. Через К-2 это работает даже без живой сессии.

### Н-1. Ключ из Identify привязан только к соединению

Для подключённой ноды это приемлемо: Noise подтверждает PeerId. Но формат `;onion=` в свободной строке `agent_version` не подписан, не имеет срока и не годится для пересылки третьим лицам — отсюда В-2.

### Н-2. Trace onion-маршрутов

`network.rs:49-131`. Последние 8 маршрутов (PeerId адресатов и hop'ов) держатся в памяти и уходят в UI. Это метаданные на устройстве. Допустимо, но стоит выключать по умолчанию.

## 4. План устранения

### Этап 0 — срочные патчи без смены формата (1–2 недели)

| # | Что сделать | Закрывает |
|---|---|---|
| 0.1 | `OnionDrop` принимать только от пира из `bootstrap_peer_ids`, у которого есть onion-ключ и живое соединение. Внутри разрешать только `Hello`, `Encrypted`, `Ack`. Остальное отбрасывать. | К-1, С-6 (часть) |
| 0.2 | Непрошеный `PrekeyOffer` игнорировать. Принимать только как ответ на свой `PrekeyGet`, только от bootstrap. Не перетирать ключ, полученный из проверенного `Hello`. | К-3 (часть) |
| 0.3 | `BootstrapGossip` с `onion_keys` принимать только от настроенных вручную bootstrap. Не перезаписывать существующий onion-ключ. Не менять PeerId у известного `ip:port`. Подмешанные ноды не сохранять до успешного Identify. | В-2 (часть) |
| 0.4 | Транзакционная расшифровка в `SecureSession`: работать на копии состояния, применять только после успешного AEAD. Ограничить скачок `n`/`pn` (например, 1000). | В-5 |
| 0.5 | Не засчитывать `Ack` от entry-hop'а как доставку. Ставить «✓» только по сквозному E2EE-подтверждению от Боба. До него держать сообщение в повторах. | В-4 |
| 0.6 | Режим «строгий onion» (по умолчанию включён, когда есть ≥3 hop'а): при неудаче wrap не слать напрямую, а ставить в очередь или в офлайн-ящик. Показывать в UI маршрут каждого сообщения: onion / прямо. | В-3 |
| 0.7 | `OfflineMailboxQuery` выполнять только если `peer == recipient` (PeerId подтверждён Noise). Лимит числа получателей и общего объёма ящика. То же на bootstrap_node. | С-5 |
| 0.8 | `DialBack` принимать только от контакта с живой E2EE-сессией и только с адресами через известные bootstrap-relay. | С-6 |
| 0.9 | Входящий `Hello` при живой сессии не сбрасывать её сразу: требовать новизну (см. 1.6) или ограничить частоту сбросов. | С-1 (часть) |

### Этап 1 — `VOID_ONION_v2` (смена формата, 4–6 недель)

1. **Убрать `src` из `OnionDrop`.** Отправитель должен определяться только внутри E2EE:
   - для `Encrypted` — поиск сессии по `header.dh_pub` (у Боба он уникален на сессию);
   - для первого `Hello` — `Hello` запечатывается к static-ключу Боба (sealed sender), а подпись внутри уже привязывает PeerId;
   - ответ — по сессии, а не по `src` из заголовка.
   Тогда exit видит только «кому» и не видит «от кого».
2. **Подписанные дескрипторы hop'ов:** `{peer_id, onion_pk, epoch, not_after, sig_ed25519(peer_id)}`. Gossip принимает запись только если подпись сходится с ключом из `peer_id`. Ротация ключа на каждую эпоху (например, неделя), а старый секрет удаляется после окончания эпохи + запаса. Это даёт ограниченную по времени прямую секретность (С-3).
3. **Бинарный формат ячеек и фиксированный размер:** bincode/CBOR вместо JSON. Набор размеров ячеек (например, 2 KiB / 16 KiB / 64 KiB), выравнивание каждого слоя до размера ячейки, одинаковый размер на всех hop'ах (Sphinx-подобная схема или хотя бы padding до бакета). Большие файлы — только через живой канал или ящик, не через onion.
4. **Защита от повтора на hop'е:** кэш `H(eph)` на время эпохи ключа. Повторы отбрасываются.
5. **KDF:** `info = "VOID_ONION_v2" || eph_pk || hop_pk`, отказ при нулевом общем секрете.
6. **Новизна `Hello`:** в подпись добавить `timestamp` и случайный `nonce`, хранить окно (например, ±10 мин) и кэш увиденных nonce.
7. **Выбор пути:**
   - постоянный guard (entry) на недели;
   - middle и exit — из разных операторов и подсетей (/16 IPv4, /32 IPv6);
   - цепочка живёт на время разговора или N минут, а не одного пакета;
   - никогда не ставить одну ноду в entry и exit одновременно;
   - при <3 независимых hop'ах в UI показывать статус «маршрут не анонимен», а не «onion».
8. **Сквозное подтверждение:** E2EE-receipt от Боба обратным onion-путём; `Ack` hop'ов означает только «принято hop'ом».

### Этап 2 — офлайн-конверт v2 и prekey (3–4 недели)

1. **Аутентифицированный конверт:**
   - внутри шифртекста лежат `sender_peer_id`, `sender_static_pk` и подпись Ed25519 над `recipient || message_id || kind || eph || H(plaintext)`;
   - получатель проверяет подпись и сверяет `sender_static_pk` с ключом контакта из `Hello`;
   - открытые поля `sender` и `sender_pk` убрать: нода видит только `recipient`.
   Альтернатива — схема «static + ephemeral» (как Noise `X`) для неявной аутентификации.
2. **Подписанные prekey:** `{x25519_pk, not_after, sig_ed25519(peer_id)}` на bootstrap и в DHT. Клиент без проверки подписи не принимает. Ротация prekey. Опционально — одноразовые prekey (X3DH).
3. **Проверка записей Kademlia:** валидатор записей `/void/prekey/*` и `/void/mailbox/*` (подпись владельца, срок), а не `MemoryStore` без проверки.
4. **Группы:** состояние группы подписывает создатель (или админ), у состояния монотонная версия, принимать только более новую версию с верной подписью.

### Этап 3 — проверка и процесс (параллельно)

- Fuzz-тесты разбора `V1Packet`, `OnionPayload`, `OfflineEnvelope` (cargo-fuzz).
- Property-тесты Double Ratchet: порядок, потери, дубликаты, мусорные заголовки не ломают сессию.
- Интеграционные тесты на каждую атаку из раздела 3: подмена `src`, непрошеный `PrekeyOffer`, gossip-Sybil, повтор `Hello`, забор чужого ящика.
- `cargo audit` и `cargo deny` в CI (это уже рекомендовано в `SECURITY_REVISION.md`).
- Требования к hop'у в bootstrap_node: кэш повторов, лимит размера ячейки, проверка `next` как PeerId, лимит частоты, отсутствие логов `next` и `src`.
- Внешнее криптографическое ревью после этапов 1–2.
